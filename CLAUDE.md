# CLAUDE.md - Task Pilot

Локальный конвейер полного цикла задачи Jira: доска, ветка, код, коммит, пуш, PR, сборка, деплой на тестовый стенд,
тест на стенде, артефакты в Jira. Интерфейс в браузере, сервер на localhost. Проект не знает конкретной команды: ее
репозитории, стенды, доска, дашборды и скиллы лежат в пакете команды, соглашения компании - в слое компании
`company/<id>`, личное - в `~/.task-pilot/profile.yaml`.

## Как устроено

- `packages/step-kit` - контракт шага: типы (`StepModule`, `StepContext`, порты, запрос и итог агента),
  zod-схемы манифестов, профилей и пресетов, контракты значений контекста (`contracts.ts`: схемы и выведенные из
  них типы `Plan`, `Changes`, `Build`, `QaReport` и другие, реестр `CONTEXT_SCHEMAS`, проверка `checkOutputs`),
  чистые функции (`planMilestone`, `findTransition`, `deployBlockReason`, `pickRepo`, `extractAcceptanceCriteria`),
  линтер публикуемых текстов (`lintText`), подстановка в шаблоны промптов (`renderTemplate`), расчет воронок фич
  (`funnel.ts`) и пути одной попытки входа (`attempt.ts`).
- `packages/api-types` (`@task-pilot/api-types`) - типы ответов API сервера: пакет содержит только типы, их
  импортируют и сервер, и веб, поэтому веб не лезет в `apps/server/src`.
- `apps/server` - Fastify на 127.0.0.1:5176: HTTP API (`http/server.ts` - приложение, охрана запросов с localhost и
  обработчик ошибок, маршруты по фичам в `http/routes/`: каталог и пресеты, настройки, интеграции, задачи, прогоны,
  API агентов, мониторинг и общий поток; общие помощники в `http/support.ts`), движок прогонов (`engine/engine.ts`),
  каталог шагов с горячей перезагрузкой (`catalog/catalog.ts`), хранилище на `node:sqlite` (`store/db.ts`, файл
  `.data/task-pilot.db`: прогоны, шаги с черновиками, замечаниями владельца и настройками, контекст, события,
  подтверждения, вопросы агентов, вопросы владельца о прогоне, сессии агентов, аккаунты интеграций, дневные итоги
  фич, правки и версии мониторинга), адаптеры (`integrations/`: Jira через MCP-сервер
  из профиля доски (`mcp` в `jira.yaml`, по умолчанию `atlassian`) из `~/.claude.json`,
  Confluence через тот же MCP (`confluence-mcp.ts`), Bitbucket через MCP-сервер контура, Bamboo через REST с токеном
  MCP-сервера контура (`bamboo-rest.ts`), логи стендов через Kibana (`kibana.ts`), логи прода напрямую из кластера
  источника `monitor.yaml` (`es-logs.ts`), git через CLI, оболочка для сборок в песочнице за портом `sandbox.ts`; доступ к ним дает сервис
  интеграций `service.ts` с реестром `registry.ts`, хранилищем токенов в Keychain `secrets.ts`, запросами "кто я" `whoami.ts` и аккаунтами CLI claude
  `claude-cli.ts`), агентный раннер (`agent/`), открытие задачи и прогоны мастера шагов (`tasks.ts`: загрузка из Jira, AC, подбор репозитория,
  фильтры экрана задач по спринту), что выкачено на стендах (`stands.ts`), фоновый наблюдатель ожиданий шагов и задач
  (`watch.ts`), журнал прогона (`journal.ts`), порт самого Task Pilot с проверкой правок на копии (`pilot.ts`),
  правка пресетов (`catalog/presets.ts`), панель мониторинга (`monitor/`: порт дашбордов, профилей фич и профиля пути
  `port.ts`, сервис экрана `service.ts`, воронки фич `features.ts`, путь одной попытки `attempts.ts`, правка по запросу
  `edits.ts`; разовый импорт истории скилла воронок - `features-import.ts`), SSE-события.
  `app.ts` собирает приложение (`startApp`: хранилище, каталог, движок, агенты, HTTP) с портами внешних систем,
  которые ему передают, и закрывает его по сигналам (`exitOnSignals`). Точки входа: `main.ts` с настоящими
  адаптерами, `demo.ts` с подмененными Jira и Bitbucket (`demo/fixture.ts`, вложения и комментарии Jira в памяти -
  `demo/jira-files.ts`), Bamboo и логами стендов (`demo/ci.ts`), вики в памяти (`demo/wiki.ts`), со сценарным агентом
  и подменным QA-браузером (`demo/agent.ts`), подменными логами прода (`demo/logs.ts`), интеграциями с токенами в
  памяти и подменными проверками (`demo/integrations.ts`) и `launcher.ts` - запуск и остановка
  для приложения в Dock и команд `pnpm start`, `pnpm stop` и `pnpm restart` (логика в `launcher/control.ts`).
  QA-браузер Task Pilot - `qa/browser.ts` с драйвером `qa/driver/` (`cdp.mjs`, выгрузка логов `kibana_logs.mjs`: у
  драйвера нет умолчаний команды, что выгружать, всегда задает сервер), файлы артефактов задачи для галереи - `artifacts.ts`, время прогонов -
  `timing.ts`, прогноз времени прогонов - `forecast.ts`, подробности событий ленты - `feed.ts`, место на диске и
  очистка кэша - `cache.ts`, вопросы владельца о прогоне - `ask.ts`, профиль команды и личных настроек для панели
  интерфейса - `profile.ts`. Учебная фича и путь одной операции демо - `demo/features.ts`.
- `apps/web` - React + Vite + Tailwind на 127.0.0.1:5177, прокси `/api` на сервер. Экран прогона слушает поток его
  событий (`useRunEvents`); при подключении сервер отдает историю прогона, поэтому перечитывания прогона, стендов
  и галереи копятся и уходят одной пачкой не позже чем через 150 мс (`batchRefresh` и `refreshKeysOf` в `refresh.ts`).
  Общий поток событий (`useGlobalEvents`) обновляет карточки задач и дает уведомления браузера (`notify.ts`).
  Шапка (`App.tsx`): разделы и их подвкладки - `nav.ts`, поле "Открыть задачу" - `OpenTask`, "Ждут вас" -
  `AttentionMenu` (`attention.ts`, `GET /api/attention`), история уведомлений - `NoticesMenu` (`notices.ts`,
  `GET /api/notifications`), кнопка и панель профиля - `ProfilePanel` (`profile.ts`, `GET /api/me`); заголовок экрана
  с пояснением в значке подсказки - `PageHeader` в `ui.tsx`, там же выпадающая панель и панель справа. Тема - `theme.ts`: класс `dark` на html, до React его ставит скрипт
  в `index.html`, поэтому варианты `dark:` Tailwind идут от этого класса, а не прямо от темы системы. Группы шагов
  прогона и строка прогноза - `progress.ts`, фильтр доски по прогону - `board.ts`.
- `steps/<id>/` - шаги: `step.yaml` (манифест), `index.ts` (реализация), промпты агента (`*.md`) и тест.
  `steps/_shared/` - общие помощники агентных шагов и правила для промптов, `steps/_test/` - помощники тестов
  шагов. `steps/_planned.yaml` - шаги плана, которые еще не реализованы. Папки и файлы с `_` в начале шагами
  не считаются.
- `pipelines/*.yaml` - пресеты.
- Слои профилей (`config.ts`: `loadTeam`, `teamLayers`, `loadProfiles`). Пакет команды - папка с `team.yaml`,
  путь к ней задает `team` личных настроек или `TASK_PILOT_TEAM`; без пакета сервер не запускается. `team.yaml`
  (`teamManifestSchema`) называет команду, слой компании (`company: <id>` - папка `company/<id>` проекта) и скиллы:
  `qa.skill` для теста на стенде с логами по умолчанию `qa.logs`, `wiki.skill` и `wiki.space` для страницы вики. В
  пакете `profiles/` (репозитории, стенды, доска `jira.yaml`, сервисы `monitor.yaml`, `lint.yaml`, `logs.yaml`),
  `dashboards/<id>/dashboard.yaml` (формат в `docs/dashboards.md`), воронки фич `features/<id>.yaml` и путь попытки
  `attempt.yaml` (формат в `docs/monitor.md`), `plugin/` (плагин агентов) и `rules.md` (правила
  текстов команды для агентов). Слой компании лежит под профилями команды: контуры с соглашениями их Bamboo
  (`prodLike`, `defaultStand`, `builds`, `serviceHeader`), репозитории конфига деплоя, источники логов стендов, адрес
  Jira и id ее полей, источник логов прода и часовой пояс панели. Контуры, репозитории, стенды и источники логов слоев складываются, одинаковый
  id - ошибка запуска; в `jira.yaml` и `monitor.yaml` ключи команды заменяют ключи компании, списки `lint.yaml`
  объединяются. Профиль репозитория ссылается на репозиторий своего конфига деплоя полем `deployRepo`. Учебная команда
  `examples/demo` - пакет демо, смоука и эталонов (`DEMO_TEAM`), пакет тестов - `apps/server/test/fixtures/team`.
- Личное - `~/.task-pilot/profile.yaml` (путь меняет `TASK_PILOT_PERSONAL`, схема - `personalProfileSchema`): путь к
  пакету команды, логин в Jira, JDK 21 для сборок Java, пути к репозиториям на своей машине, репозиторий по умолчанию,
  дополнительные имена для линтера и личный стиль текстов `style` (е, тире, кавычки). `loadProfiles` накладывает их на
  профили слоев (`applyPersonal`): JDK достается только сборкам Java без своего `build.javaHome`, неизвестный репозиторий
  или поле в файле - ошибка запуска. Шаг `jira.start` отказывается назначать задачу, пока логин не задан ни там, ни
  токеном с экрана "Интеграции".
- Плагин агентов - `plugin/` пакета команды (другой задает `TASK_PILOT_PLUGIN`): агенты получают его флагом
  `--plugin-dir` (`pluginDir` в `buildClaudeArgs`), шаги берут папки скиллов команды из `StepContext.team`
  (`stepTeamOf`, `teamSkill` в `steps/_shared/team.ts`), разбор прогона правит их по `PilotPort.skillsDir`. Личные
  скиллы владельца в `~/.claude/skills` Task Pilot не трогает и агентам не подсовывает. Правила для агентов, которые не
  должны зависеть от личного `~/.claude/CLAUDE.md` (публикация, песочница, имена), лежат в `steps/_shared/rules.md` и
  `rules-code.md`; `agentRules(c)` добавляет к ним правила команды и личный стиль (`StepContext.texts`).
- `launcher/` - приложение для Dock: иконка `icon.svg`, программа `TaskPilot.swift` (свое окно с интерфейсом на
  WebKit) и сборка `install.sh`.

Реализованы шаги этапов 1-5: `jira.start`, `git.prepare`, `task.analyze`, `task.rework`, `code.implement`,
`code.verify`, `code.publish`, `ci.wait`, `ansible.config`, `deploy.stand`, `qa.stand`, `qa.fix`, `qa.publish`,
`pr.address-review`, `task.finish`, `wiki.update`, `pilot.retro`, мастер `pilot.new-step`, и шаг этапа 6
`monitor.dashboard`; шаг, который описан в `_planned.yaml`, но еще не реализован, интерфейс показывает серым с номером
этапа. Пресет `full` идет в порядке `jira.start`, `git.prepare`, `task.analyze`, `code.implement`, `code.verify`,
`code.publish`, `ci.wait`, `ansible.config`, `deploy.stand`, `qa.stand`, `qa.fix`, `qa.publish`, `pr.address-review`,
`monitor.dashboard`, `wiki.update`, `task.finish`, `pilot.retro` (дашборд и вики - фоновые шаги, они готовятся, пока
`task.finish` ждет мерж); `ansible.config` и `monitor.dashboard` в нем по умолчанию выключены.
Пресет `monitor` из одного `monitor.dashboard` открывает кнопка "Собрать дашборд" на обзоре мониторинга. Пресет `code-pr`
заканчивается на `code.publish`, `hotfix` идет без `task.analyze`, и `code.implement` тогда работает по описанию
задачи без плана, `test-stand` начинается с готовой ветки: `ci.wait`, `deploy.stand`, `qa.stand` и `qa.publish`, без
доработки (в нем нет шагов кода). `rework` начинается с `task.rework` и проходит ветку, код, проверку, публикацию,
сборку, деплой, тест, доработку, итоги, ответ на ревью и мерж. `finish` для задачи после ревью: ответ на замечания
и мерж с вики, а проверку, коммит и сборку в нем включает петля ответа на ревью. `new-step` - прогон мастера
"Новый шаг". Пресет выбирается в карточке прогона и меняет шаги этого же прогона, новый прогон заводит только
кнопка "Новый прогон" (см. правила движка). Пресеты правятся на экране "Пресеты" (`docs/pilot.md`); шаг в пресете
стоит после шагов, которые дают нужные ему ключи (`presetOrderIssues`), иначе пресет не сохраняется.

## Запуск и проверка

```bash
pnpm install
pnpm dev        # сервер и интерфейс, http://127.0.0.1:5177
pnpm demo       # демо-режим, http://127.0.0.1:5187 (сервер на 5186)
pnpm demo:script  # то же со сценарным агентом вместо CLI claude, лимит подписки не тратится
pnpm check      # typecheck + тесты + сборка интерфейса
pnpm checkup    # проверка окружения машины, то же на вкладке "Настройки / Окружение"
pnpm smoke      # смоук интерфейса: главные экраны и панели шапки демо в headless Chrome, его же запускает хук перед коммитом
pnpm reference  # эталонные задачи DEMO-1 и DEMO-2 с настоящими агентами, около $1.5; --script - со сценарным
pnpm features:import  # разовый импорт истории дней воронок из скилла feature-stats в базу
pnpm app        # собрать приложение ~/Applications/Task Pilot.app со своим окном интерфейса
pnpm start      # запустить в фоне, как иконка; pnpm stop - остановить
pnpm restart    # перезапустить после правок сервера, приложение в Dock продолжает работать
```

Сервер, запущенный приложением или `pnpm start`, правки кода сам не подхватывает: после изменений в
`apps/server/src`, `step-kit`, `company/` или в `team.yaml` и профилях пакета команды нужен `pnpm restart`, а при
выполняющемся прогоне он откажется.
Подробности запуска, проверки окружения, смоука, эталонов и копий базы - в `docs/operations.md`, демо-режим -
в `docs/demo.md`.

Сборка не нужна: Node 26 запускает `.ts` напрямую. Отсюда ограничения синтаксиса (`erasableSyntaxOnly`):
нельзя enum, namespace и параметр-свойства конструктора (`constructor(private x)`), импорты с расширением `.ts`,
типы импортируются через `import type`. Сервер в dev (`apps/server/src/dev.ts`) перезапускается при правке `src`,
`step-kit`, `company/` и профилей пакета команды;
шаги и пресеты подхватываются без перезапуска, включая вспомогательные файлы шага: хук загрузчика
`installReloadHook` в `catalog.ts` прокидывает метку перезагрузки на локальные импорты шага, в том числе на
`steps/_shared`. Промпты шагов читаются при каждом запуске агента.

Агентным шагам нужен CLI claude под входом владельца: путь задает `TASK_PILOT_CLAUDE`, по умолчанию
`~/.local/bin/claude`. Перезапуск сервера прерывает прогоны: шаг в работе падает с ошибкой "Прервано
перезапуском сервера", прогон встает на паузу, агенты и сборки останавливаются, а `code.implement` при повторе
продолжает прерванную сессию агента. Шаг, который ждет события (сборки, деплоя, мержа), не выполняется: перезапуск его
не прерывает, после старта его продолжает наблюдатель. Прогоны, в которых еще ничего не выполнялось, при старте сервера и при
открытии задачи подстраиваются под текущий пресет (`Engine.syncSteps`): порядок шагов и выбор только что
реализованных шагов; то, что владелец включал или выключал сам, сохраняется.


## Правила движка, которые нельзя ломать

- Выходы шага проверяются контрактами (`CONTEXT_SCHEMAS` или `contracts` модуля шага) до записи в контекст:
  значение не по контракту роняет шаг, и контекст не меняется ни одним ключом. Каждый ключ `provides` реализованного
  шага имеет контракт, иначе каталог показывает ошибку. Шаги не импортируют модули друг друга: общие типы в
  step-kit, общие функции в `steps/_shared/`.
- Ядро и веб не знают шагов по id: что устарело на экранах после шага (`refresh`), нужен ли его агенту QA-браузер
  (`agent.browser`), как называется его петля (`loop.title`) и по какому событию вне прогона он запускается заново
  (`trigger`), задает манифест. Событие прогона запускает его шаг с `trigger` на это событие и `auto` (`Engine.onEvent`:
  замечания в PR - ответ на ревью), кнопка "Доработать" на плашке изменений задачи - шаг с
  `trigger.event: issue.changed` пресета "Доработка".
- Агент и шаг не делают внешних действий в обход подтверждения: шаги с `gate: publish` спрашивают всегда,
  с `gate: before` - когда preview не сказал `requiresApproval: false`.
- Шаг выполняется в порядке `done`, пробный прогон (`simulate`), `prepare`, `preview` с проверкой текстов,
  подтверждение, `run`. `prepare` вызывается, только когда черновика нет или владелец вернул шаг с замечанием:
  подтверждение не запускает агента заново, а `run` публикует черновик, который видел владелец.
  "Переделать" передает замечание в `prepare`, "Повторить" стирает черновик. Замечание к повтору ("С замечанием")
  агент шага получает в каждом задании следующей попытки вместе с ошибкой прошлой, и оно стирается с началом
  попытки; шагу без агента его передать некому, и движок его не принимает.
- Настройки шага (`params` манифеста) - выбор прогона поверх умолчания пресета и манифеста (`effectiveParams`).
  У идущего шага они не меняются; подтверждение шага, который его ждал, сгорает, и шаг сразу спрашивает заново уже
  с новыми настройками.
- Подтверждение одноразовое и привязано к `stableHash` от `preview.payload` вместе с `preview.texts` без их
  `format`: изменилось содержимое или хоть одно слово текста - подтверждение сгорает. Смена стенда или режима прогона
  сжигает ожидающие и еще не израсходованные подтверждения. Запросы шага, который прошел без подтверждения
  (сделан раньше, пропущен, повторен или больше его не требует), тоже сгорают.
- Публикуемые тексты (`texts` с `publish: true`) движок проверяет линтером заново. Пустой текст, текст, который
  линтер еще исправил бы, секреты, телефоны, адреса почты и имена сотрудников из `lint.yaml` слоев блокируют
  подтверждение, и API его не примет. Исключение - текст с `stepLinted: true` (обновляемая страница вики с чужими
  строками): его шаг проверяет сам по новым и измененным строкам и кладет замечания в `lint` превью. Отказ не
  принимается, пока идет то, что дошло бы до шага и спросило снова: у шага цепочки - цепочка, у фонового шага - он сам.
- Два прогона одной задачи не выполняются одновременно: они работали бы в одной рабочей папке.
- Фоновый шаг (`background: true` в манифесте) не держит цепочку отмеченных шагов. Он стартует, когда отмечен и в
  ожидании, отмеченные шаги цепочки выше него закончены, а его `requires` есть в контексте, и идет рядом со
  следующими шагами тем же порядком `done` - `run` с общим сигналом остановки. Его агент не пишет в рабочую папку
  (`writeCwd: false` ставит движок), ожидание внешнего события у него - сбой, петлей он быть не может (ошибка
  каталога). Упавший фоновый шаг цепочку не останавливает, отклоненный становится `blocked` и сам не стартует снова;
  прогон `completed`, только когда закончены все отмеченные шаги. Параметры прогона меняются, только когда в нем ничего
  не идет.
- Подтверждений у прогона может быть несколько, у шага цепочки и у фоновых шагов: `approvals` в порядке запросов,
  `approval` - первое из них. Одобрение и "Переделать" фонового шага запускают только его. Статус прогона при
  совмещении: `waiting_owner` важнее `running`, `running` важнее статуса цепочки.
- Смена пресета не заводит прогон, а меняет шаги этого (`applyPreset`): шаги и отметки нового пресета, выполненные
  шаги не из него остаются в начале списка неотмеченными как история, их результаты остаются в контексте,
  невыполненные шаги не из пресета удаляются вместе с черновиками. Подтверждение сгорает, как при любой смене
  параметров, а статус прогона пересчитывается по новому набору шагов (`settleStatus`).
- После выключения пробного прогона имитированные шаги возвращаются в ожидание, а их выходы убираются из
  контекста.
- Агент не публикует: `baseDeny` запрещает git push и commit, прямую сеть, чтение файлов с токенами и пишущие
  инструменты MCP, и разрешения шага этого не открывают. Пишущие инструменты запрещаются на серверах, которые называют
  профили (`mcpWriteTools`: сервер доски и серверы Bitbucket и Bamboo контуров), а не по списку имен. Публикует только
  код шага в `run` после подтверждения. MCP-серверы владельца агент получает только по списку шага.
- На вопрос владельца о прогоне отвечает агент, который только читает (`AskService`, `ask.ts`): Read, Grep и Glob
  без MCP-серверов, записи и вопросов владельцу. Его работа в ленту не пишется, а стоимость ответа входит в расход
  агентов, но не во время и стоимость прогона.
- `.claude/` не коммитится никогда: `code.publish` коммитит только пути из `commitPaths` профиля за вычетом
  `NEVER_COMMIT` (`.claude/`, `.env`, `.DS_Store`, `.idea/`, `*.iml`), снимает из индекса чужие пути, передает
  пути git буквально и сверяет id блобов с подтвержденными после `git add` и после коммита: изменился файл или
  хук переписал коммит - пуша нет. Ветка, переписанная ребейзом, пушится только с `--force-with-lease` на
  версию, которую видел владелец, и только если у каждого коммита remote есть эквивалент в ветке; если ветка
  отстает или на remote чужие коммиты, публикация блокируется. При конфликтах и незаконченных merge, rebase
  или cherry-pick шаг не публикует.
- Петля доработки (`loop` в манифесте) перезапускает только шаги из `restart`, которые есть в прогоне, и сам шаг
  петли; их черновики и подтверждения сгорают, результаты остаются в контексте, круги считаются в `loops`.
  Проверка лимита идет до выполнения шага петли, но после его `done`: когда дорабатывать нечего, лимит не мешает.
- Шаг, который ждет внешнего события, бросает `StepWaiting` с событием и сроком: это не сбой, шаг и прогон получают
  статус `waiting`, прогон продолжает наблюдатель, а после срока он роняет шаг (`failWaiting`). Ожидание из `run`
  шаг с `resume` продолжает без `done` и без нового подтверждения; шаг без `resume` и ожидание до подтверждения идут с
  начала. Повтор и пропуск ждущего шага снимают его ожидание. Хук `again` шага петли решает, начинать ли новый круг
  после успешного запуска; без хука - всегда.
- Правки файлов самого Task Pilot (разбор прогона, мастер шагов) агент пишет только в отдельную папку, проверка
  идет на копии в песочнице, а записывает код шага после подтверждения; коммитит их только владелец.
- Отметка шага - план: она меняется только у шага, который еще не начинался. "Пропустить" есть только у шага, на
  котором прогон остановился (упал, заблокирован, ждет подтверждения или события), и сразу продолжает прогон.
- Прогон, которому задача не подсказала репозиторий (`repoChoice.unsure`), не запускается, пока владелец не выберет
  репозиторий: код не пишется в репозиторий по умолчанию молча.
- Упавший шаг цепочки останавливает прогон, пока владелец его не повторит или не пропустит. "Остановить" завершает
  агента и сборку текущего шага цепочки и идущих фоновых шагов через общий `AbortSignal`: шаги падают с ошибкой
  "Остановлено владельцем", следующие шаги не запускаются.
- В пробном прогоне шаги с `sideEffects: true` вызывают `simulate`, а не `run`; `prepare` у них не вызывается,
  и агент не запускается.
- Все сообщения, ошибки, контекст, превью и вопросы агентов проходят через `Redactor`: токены из
  `~/.claude.json` и с экрана "Интеграции" маскируются, в том числе в журнале потока агента, а линтер не пропускает
  их в публикуемые тексты. Токен в ответы API не попадает никогда: экран видит только его последние символы.
- Деплой только на стенды, для которых `deployBlockReason` вернул null. Окружения прода запрещены в профиле контура
  (`forbiddenBambooEnvIds`) и отсекаются по имени namespace и окружения: слово prod - всегда, остальные имена прода -
  `prodLike` контура. Порт Bamboo сам отказывает в деплое на окружения вне стендов: токен технически разрешает деплой
  и на прод. Токен Bamboo уходит только на хост Bamboo своего контура.
- API принимает запросы только с localhost; изменяющие запросы требуют заголовок `x-task-pilot: 1`, маршруты
  `/api/agent/*` - еще и токен запуска агента.

## Правила вне движка

Правила из тем в `docs/`, которые действуют при любой правке:

- Сборки и команды агентов идут только в песочнице: без доступной песочницы (`Sandbox.available()`, на macOS -
  `sandbox-exec`) сборка не запускается, а в профиле песочницы нет правила `(local ip ...)` для исходящих соединений:
  вместе с DNS через localhost оно пропускает любой трафик.
- Токен git для Bitbucket передается только через `GIT_CONFIG_COUNT` и `http.<адрес>.extraHeader` для хоста этого
  Bitbucket, никогда в аргументах процесса; токен в Keychain пишется через stdin в шестнадцатеричном виде.
- Task Pilot не ходит молча под другим доступом, чем выбран: не прочитался токен активного аккаунта - интеграция
  возвращается к доступу как обычно с объяснением в ленте.
- Сервер отклоняет любой запрос с меткой QA-браузера `TaskPilotQA`: из QA-браузера нельзя открыть интерфейс или API и
  подтвердить свой же шаг.
- Логи прода панель мониторинга только читает: всегда граница по времени, не больше двух запросов одновременно,
  ограничения живут в `integrations/es-logs.ts`; поля куки, заголовков, токенов и паролей (`FORBIDDEN_FIELD`) порт не
  читает никогда.
- Телефон, код и IP из логов прода видны только на экране пути попытки: поиск и путь идут POST-запросом, в адрес
  страницы, базу, ленту и журналы они не попадают, агентам уходят маской (`maskPhones`).
- Правку мониторинга по запросу агент возвращает текстом файла и ничего не пишет сам: файл пакета команды пишет
  "Применить" после проверки схемой, прежний текст остается версией (`docs/monitor.md`).
- На пресеты `full`, `rework` и `new-step` опирается код (`PROTECTED_PRESETS`): их можно править, но не удалять.
- Слои без данных конкретного человека: личное - в `~/.task-pilot/profile.yaml`. Знание команды (ее сервисы,
  стенды, доска, соглашения, слова) - в ее пакете: в профилях, `rules.md` и скиллах, а не в коде и промптах проекта;
  соглашения компании - в `company/<id>` или, если слоя компании нет, в пакете команды.
- Новую компанию заводят по `docs/new-company.md`: ее данные (адреса, id окружений прода и полей Jira, имена
  MCP-серверов) спрашиваются у владельца или берутся из самих систем, а не придумываются; вариант, где лежат профили
  компании, выбирает владелец.

## Как добавить шаг

Подробно: `docs/adding-a-step.md`. Коротко: папка `steps/<область>.<действие>/`, `step.yaml` по схеме
`stepManifestSchema`, `index.ts` с `export default` объекта `StepModule` (`run` обязателен, `done` делает шаг
идемпотентным, `prepare` готовит черновик до подтверждения и переделывает его по замечанию, `preview` нужен
шагам с подтверждением, `simulate` - пробному прогону), тест рядом (`*.test.ts`). Агентный шаг задает модель
и бюджет в разделе `agent` манифеста, промпт держит рядом в `prompt.md` (подстановка `renderTemplate`)
и добавляет общие правила `agentRules(c)`; публикуемые тексты пропускает через `c.lint`. Если шаг был
в `_planned.yaml`, запись там можно оставить: реализация ее перекрывает.

## Тесты

Каждое изменение поведения сопровождается тестами; имя теста описывает гарантию. Движок тестируется
на `Store(':memory:')` и `FakeCatalog` (`apps/server/test/helpers.ts`), шаги git - на временных репозиториях
(`branchRepo` в `steps/_test/git.ts`), шаги Jira - на фейковом порте, агентные шаги - на `fakeAgent`
и `testContext` (`steps/_test/context.ts`). Профили в тестах - пакет `apps/server/test/fixtures/team` над слоем
`company/example` и учебная команда `examples/demo`: тесты не читают пакет команды владельца. Какой тест что покрывает -
`docs/tests.md`.

## Git

Репозиторий локальный, remote не выбран. Коммиты только по просьбе владельца, `.claude/`, `.data/` и
`node_modules/` не коммитятся. Локальный CI - хук `.githooks/pre-commit`: он запускает `pnpm check` по рабочей папке,
затем смоук интерфейса `pnpm smoke`, и отменяет коммит, если что-то красное, показывая конец вывода. Переменные `GIT_*`, которые git передает хукам
(`GIT_INDEX_FILE` и другие), хук перед проверкой убирает: с ними git в тестах с временными репозиториями работал бы с
индексом этого репозитория. Хуки включает `pnpm install` (скрипт `prepare` ставит
`core.hooksPath`), проверку пропускает только `git commit --no-verify` по решению владельца.
