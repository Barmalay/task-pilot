Как работать:

1. Прочитай скилл {{skill}}/SKILL.md и справочник {{skill}}/references/services.md: в справочнике - как проверять сервисы команды на их стендах, в скилле - порядок прогона, правила кадров Kibana и формат отчета. Код сервиса лежит в рабочей папке: адреса, тела запросов, ответы и строки логов бери из него.
2. Для каждого AC выбери путь по сути проверки. Что видно на экранах входа - через вход Keycloak в QA-браузере, если он проверяет эту сборку (см. выше). Что проверяется ответами сервиса - запросами к его API.
3. Браузер - QA-браузер Task Pilot, он уже запущен, и владелец его видит. Управляй им только инструментом mcp__pipeline__qa_browser (найди его через ToolSearch): действия драйвера QA-браузера перечислены в его описании. Запросы к API сервиса делай из вкладки, открытой на его адресе: действие navigate на {{serviceUrl}}{{health}}, затем eval с fetch по пути от корня сервиса; из eval возвращай статус, заголовок X-Environment и тело ответа. X-Environment должен быть {{namespace}}: другое значение значит, что ответил другой стенд, а сервиса на {{stand}} нет, и такой ответ доказательством не считается.
4. Логи сервиса выгружай инструментом mcp__pipeline__qa_kibana_logs с service "{{service}}": выгрузка идет по namespace {{namespace}}, без service приходят логи, которые команда задала по умолчанию (qa.logs в team.yaml). Вкладка Kibana должна быть открыта. Ссылку Kibana для кадра логов сервиса собирай командой python3 {{skill}}/scripts/kibana_url.py '<from>' '<to>' '<KQL>' {{service}} '{{dataView}}' level,messagetext {{namespace}}, она сети не требует; поле текста в логах сервиса - messagetext.
5. Скриншоты делай действием shot с именами по сценариям (01-..., kibana-logs-01-...), без расширения. Они ложатся в {{artifacts}}; смотри их инструментом Read, чтобы убедиться, что на кадре то, что нужно. Ответ API снимай кадром вкладки, где он виден, или приводи в отчете статус, X-Environment и нужные поля ответа.
6. Капчу сам не решай. Если нужен владелец (капча, код из SMS, подтверждение в приложении), доведи вкладку до нужного экрана, сделай скриншот и спроси через mcp__pipeline__ask_owner, что именно сделать и в какой вкладке QA-браузера. Собирай такие действия в один-два вопроса.
7. QA-гайд: {{guide}}. Если файл есть, иди по нему и обнови; если нет, составь по AC: сценарий, что показать, что доказывает.
8. Отчет: {{report}} по разделу "Отчет" скилла: предусловия стенда, таблица AC с итогом и доказательством (имена файлов, запросы и ответы, ключевые записи логов со временем), отдельно замечания не по задаче. Если отчет уже есть с прошлого круга, обнови в нем итоги перепроверенных AC и допиши, на какой сборке их перепроверил; итоги остальных AC не удаляй: отчет уходит во вложение задачи целиком.
9. Писать можно только эти два файла. Код не меняй и ничего не публикуй: итоги в Jira публикует следующий шаг после подтверждения владельца.
10. Стенд общий. Данные смежных сервисов и настройки меняй, только если этого требует сценарий гайда, и только после ответа владельца через mcp__pipeline__ask_owner; после проверки верни как было и отметь это в отчете. Отказ смежных сервисов вызывай их штатными отказами (некорректные входные данные, лимит вызовов на один номер), а не поломкой их на стенде; если такого способа не нашел, спроси владельца, прежде чем ставить AC "не проверен". Ключ API тестового стенда (Stable, Testing-*) бери из его конфига в k8s-ansible и подставляй только внутри eval во вкладке; ключи прода, пароли и токены не бери, никакой ключ не выводи в ответы, отчет и вопросы владельцу. Токены пользователей держи внутри вкладки QA-браузера и не выводи их в ответы, отчет и вопросы владельцу.

Итог по каждому AC одним словом: пройден, не пройден, частично или не проверен (с причиной). "Не проверен" с причиной лучше натянутого "пройден". В текстах нет имен людей и номеров телефонов ("номер А", "тестовый номер"). В ответе по схеме перечисли все проверенные AC с файлами их доказательств по порядку и итог прогона одним-двумя предложениями, только факты. Ответ по схеме уходит в комментарий Jira: сценарии и причины пиши коротко, а remarks оставь пустым, замечания не по задаче остаются только в отчете.
