# Как добавить шаг цикла

Шаг - это папка `steps/<область>.<действие>/`, например `steps/jira.review/`. В ней лежат манифест
`step.yaml`, реализация `index.ts` и тест. Каталог следит за папкой `steps` и подхватывает новый шаг
без перезапуска сервера; ошибки в файлах шага видны на экране "Каталог шагов".

## Манифест

```yaml
id: jira.review            # совпадает с именем папки
title: На ревью            # как шаг называется в интерфейсе
hint: "Переводит задачу по доске на ревью"
phase: task                # task | code | ci | deploy | qa | finish | meta
kind: code                 # code | agent | hybrid | manual
requires: [issue]          # ключи контекста, без которых шаг не запускается
provides: [status]         # ключи, которые шаг кладет в контекст
gate: before               # none | before | publish
sideEffects: true          # false - шаг только читает и в пробном прогоне выполняется по-настоящему
```

Каждому ключу из `provides` нужен контракт: схема значения в реестре `CONTEXT_SCHEMAS`
(`packages/step-kit/src/contracts.ts`) или, если новый ключ кладет только этот шаг, в поле `contracts` его модуля.
Каталог показывает шаг с ключом без контракта ошибкой на экране "Каталог шагов", а свой контракт ключа, который уже
есть в step-kit, тоже ошибкой: общий контракт один. Движок проверяет выходы шага контрактами до записи в контекст:
значение не по контракту роняет шаг с ошибкой "Шаг вернул <ключ> не по контракту: ...", и контекст не меняется ни
одним ключом; ключ без контракта записывается как есть, с пометкой в ленте.

`gate: publish` - шаг меняет что-то снаружи (пуш, PR, комментарий, деплой) и спрашивает владельца всегда.
`gate: before` - спрашивает, если `preview` не вернул `requiresApproval: false`; так делает `git.prepare`,
которому подтверждение нужно только для ребейза уже запушенной ветки.

Поле `kind` описательное: по нему интерфейс показывает, кто делает шаг, а движок ведет все шаги одинаково,
и поведение задают методы модуля. Шагу с агентом манифест задает настройки запуска:

```yaml
agent:
  model: opus              # модель по умолчанию: opus для тяжелых шагов, sonnet для текстов, haiku для классификации
  effort: high             # low | medium | high | xhigh | max, необязательно
  maxBudgetUsd: 8          # предохранитель расхода на один запуск агента
```

Модель и бюджет из запроса шага перекрывают значения манифеста, `effort` берется только из манифеста.
Промпт и права агента шаг собирает сам в коде, об этом ниже. `browser: true` в разделе `agent` открывает агенту
QA-браузер Task Pilot: без него маршруты инструментов `qa_browser` и `qa_kibana_logs` откажут запуску этого шага.

Шаг доработки, после которого часть прогона нужно пройти заново, описывает это разделом `loop`:

```yaml
loop:
  restart: [code.verify, code.publish, ci.wait, deploy.stand, qa.stand]   # шаги, которые пройдут заново
  max: 3                                                                # сколько кругов можно сделать
  title: по тесту                                                       # название петли для людей
```

После успешного `run` такого шага движок возвращает в ожидание шаги из `restart`, которые есть в прогоне, и сам
шаг: их черновики и подтверждения сгорают, результаты остаются в контексте, а счетчик кругов лежит в `loops`.
Шаги из `restart` должны стоять в пресете до шага петли, иначе новый круг не дойдет до них раньше него. Чтобы петля
заканчивалась, `done` шага петли отвечает "уже сделано", когда дорабатывать нечего; если круги исчерпаны, а
дорабатывать есть что, шаг падает "Петля исчерпана", и дальше решает владелец. Неизвестный шаг в `restart` каталог
показывает ошибкой манифеста. Пример - `steps/qa.fix/`.

Если новый круг нужен не после каждого успешного запуска, модуль шага задает хук `again(c, outputs)`: он получает
выходы только что выполненного `run` и возвращает, начинать ли круг. Так `pr.address-review` начинает круг проверки,
коммита и сборки, только если по замечаниям менялся код, а ответы без правок сразу идут на публикацию.

Ядро и интерфейс не знают шагов по id: как вести себя с шагом, говорят признаки его манифеста. Все они
необязательные, интерфейс получает их в шагах прогона и каталога (`stepSigns` в step-kit).

| Поле | Значения | Что дает | Пример |
|---|---|---|---|
| `refresh` | список из `stands` и `artifacts`, по умолчанию пустой | когда шаг закончился успехом или сбоем, движок кладет список в событие `step.status`, и экран прогона перечитывает стенды или галерею артефактов | `deploy.stand`: `[stands]`; `qa.stand`, `qa.fix`, `qa.publish`: `[artifacts]` |
| `loop.title` | строка | название петли: панель контекста подписывает им круги в "Круги доработки" вместо id шага | `qa.fix`: по тесту, `pr.address-review`: по ревью, `task.rework`: по задаче |
| `trigger` | `{ event, auto }`: `event` - `pr.review` (в PR замечания без ответа) или `issue.changed` (задача изменилась в Jira), `auto` по умолчанию `false` | шаг работает по событию вне прогона: с `auto: true` его запускает наблюдатель, иначе владелец с экрана прогона; интерфейс показывает плашку "по событию" | `pr.address-review`: `{ event: pr.review, auto: true }`; `task.rework`: `{ event: issue.changed, auto: false }` |
| `agent.browser` | `true` или `false` | QA-браузер агента, см. выше; пока такой шаг выполняется, галерея артефактов на экране прогона живая | `qa.stand`, `qa.fix` |
| `background` | `true` или `false`, по умолчанию `false` | фоновый шаг идет рядом с цепочкой и ее не держит, см. раздел "Фоновый шаг"; интерфейс показывает плашку "фоновый" | `wiki.update`, `monitor.dashboard` |

Настройки шага, которые владелец может менять, задаются разделом `params`: `type` (`select`, `text`, `boolean` или
`jiraStatus`), подпись `label`, варианты `options` для `select`, значение `default`, а у `jiraStatus` обязательная
веха доски `milestone` (ключ `milestones` профиля доски `jira.yaml`, `docs/team-pack.md`). Шаг читает значения из `c.params`: выбор прогона, иначе умолчание
пресета (раздел `params` файла `pipelines/<id>.yaml`, экран "Пресеты"), иначе манифест (`effectiveParams` в step-kit).
Пример текстовой настройки - пространство вики `space` в `steps/wiki.update/step.yaml`.

Настройка `jiraStatus` говорит, куда шаг переводит задачу по доске. Ее варианты - "как обычно" (пустое значение: шаг
получает статус своей вехи), "не переводить" (`NO_MOVE`, значение `none`) и статусы доски по порядку пути. Шаг
разбирает ее общей функцией `moveOf` из `steps/_shared/board.ts` (цель и переходы по `planMilestone`, назад по доске
не двигает), а выключенный перевод показывает на подтверждении строкой `moveOffText`. Так устроена настройка `moveTo`
у `jira.start`, `code.publish`, `qa.publish` и `task.finish`. В прогоне настройки меняют кнопка "Настроить" в строке
шага и "Изменить" в окне подтверждения (`PATCH /api/runs/:id/steps/:stepId/params`, `Engine.setParams`, `null`
возвращает умолчание): у идущего шага они не меняются, остальные шаги получат их, когда выполнятся, а подтверждение
шага, который его ждал, сгорает, и шаг сразу спрашивает его заново уже с новыми настройками. Значение проверяется по
вариантам (`paramProblem`), выбор пишется в ленту событием `step.params`.

## Реализация

```ts
import type { StepModule } from '../../packages/step-kit/src/index.ts';

const step: StepModule = {
  async done(c) {
    // Уже сделано? Вернуть { note, outputs } или null.
    return null;
  },
  async preview(c) {
    // Что будет сделано. payload - то, что подтверждает владелец: изменится он - подтверждение сгорит.
    return { title: 'Перевести на ревью', actions: ['In Progress → Code Review'], payload: { key: c.run.issueKey } };
  },
  async simulate(c) {
    // Пробный прогон: ничего не менять, вернуть ожидаемые выходы для следующих шагов.
    return { status: 'Code Review' };
  },
  async run(c) {
    // Настоящее действие. Вернуть выходы - они попадут в контекст прогона.
    return { status: 'Code Review' };
  },
};

export default step;
```

Через `c` шаг получает задачу прогона (`c.run.issueKey`), данные задачи и других шагов (`c.get('issue')`,
`c.get('ac')` - их кладет открытие задачи; критерии, по которым работает прогон, дает `acOf(c)` из
`steps/_shared/ac.ts`: из описания задачи, а если их там нет - утвержденные с планом, `plan.ac`), профиль репозитория (`c.repo`) и его контур (`c.contour`: шагам с git
и Bamboo в неподключенном контуре нужно остановиться с понятной ошибкой), выбранный стенд (`c.stand`),
репозиторий конфига деплоя из `deployRepo` профиля (`c.deployRepo`), доску Jira (`c.jira`), команду прогона
(`c.team`: id и название, папки скиллов теста на стенде и вики из `team.yaml` ее пакета и пространство вики), правила
текстов команды и личный стиль владельца (`c.texts`), порты внешних систем
(`c.ports.jira`, `c.ports.git`, `c.ports.shell` для сборок и тестов, `c.ports.scm` для PR в Bitbucket,
`c.ports.bamboo(contour)` для сборок, релизов и деплоя в Bamboo контура, `c.ports.logs(stand.logs)` для образов
подов и ответа стенда, `c.ports.browser` для QA-браузера, `c.ports.wiki` для страниц Confluence и `c.ports.pilot` для
журнала прогона и проверки правок самого Task Pilot на копии), агента
(`c.agent`), папки задачи (`c.paths.docs` и `c.paths.artifacts` - рабочие доки и артефакты внутри репозитория
по `docsDir` и `artifactsDir` профиля, `c.paths.run` - служебная папка прогона `.data/runs/<id>` для журналов
сборок и временных файлов, `c.paths.agentDocs` - копия доков задачи для агента, см. "Агентный шаг"),
черновик и замечание владельца (`c.draft`, `c.feedback`), линтер текстов (`c.lint`),
сигнал остановки (`c.signal`), память на время одного выполнения (`c.scratch`) и журнал (`c.log`).
Секреты в журнале маскируются автоматически.

Типы значений, которые дают другие шаги (`Plan`, `Changes`, `Build`, `DeployedBuild`, `QaReport`, `QaFix`,
`TestReport`, `PrReview` и остальные), шаг берет из step-kit: они выведены из контрактов `contracts.ts`. Модули
других шагов не импортируются, это проверяет тест каталога; функции, которые нужны нескольким шагам, лежат в
`steps/_shared/` (`approvedPlan` в `plan.ts`, `failedOf` в `qa.ts`, `parseWorktrees` в `worktrees.ts`). Новый ключ,
который кладет только этот шаг, описывается в модуле: `contracts: { greeting: z.string() }`, `z` берется из
step-kit; когда ключ начнут читать другие шаги, его контракт переезжает в `contracts.ts`.

Синтаксис TypeScript должен стираться без компиляции: без enum, namespace и параметр-свойств конструктора,
импорты с расширением `.ts`. Вспомогательные файлы шага кладутся рядом с `index.ts` и тоже подхватываются
без перезапуска сервера.

## Черновик и доработка

Шагу, который перед подтверждением должен что-то подготовить (план, сообщение коммита, тексты PR), нужен
метод `prepare`. Он возвращает черновик - любое значение, которое сериализуется в JSON. Движок сохраняет
черновик в базе прогона и передает его в `c.draft` методам `preview` и `run`, в том числе после перезапуска
сервера. Поэтому подтверждение не запускает агента заново, а `run` публикует ровно то, что видел владелец.
Все, что нужно `run`, должно лежать в черновике или в файлах, на которые он ссылается: `c.scratch` живет только
одно выполнение шага.

Порядок выполнения шага такой. Сначала `done`. В пробном прогоне шаг с `sideEffects: true` дальше не идет:
`prepare` не вызывается и агент не запускается, план из `preview` пишется в журнал, только если черновик уже
есть, а выходы для следующих шагов дает `simulate`. В обычном прогоне движок вызывает `prepare`, если черновика
еще нет или владелец вернул шаг с замечанием, затем `preview`, проверяет публикуемые тексты линтером и ждет
подтверждения, и только после одобрения вызывает `run`. После одобрения шаг выполняется заново с новым
контекстом: `preview` вызывается еще раз, и если состояние снаружи изменилось, изменится и `payload`, а
подтверждение сгорит. `prepare`, вернувший `undefined`, сохраняет черновик `null`, и он тоже считается готовым.

На подтверждении у шага с `prepare` есть кнопка "Переделать": владелец пишет замечание, и движок сразу
запускает шаг снова. `prepare` вызывается с замечанием в `c.feedback` и прежним черновиком в `c.draft`, так что
шаг может продолжить ту же сессию агента коротким промптом с замечанием, а не начинать работу заново. После
`prepare` замечание сбрасывается (в `preview` и `run` `c.feedback` всегда `null`), новый черновик заменяет
старый, и владелец получает новый запрос подтверждения. Переделать можно только шаг с `prepare` и только
с непустым замечанием; шаг без черновика владелец отклоняет и повторяет. "Отклонить" черновик сохраняет:
при следующем запуске `preview` покажет его же. "Повторить" стирает черновик и замечание, и шаг начинается
с нового `prepare`. Упавший или заблокированный шаг с агентом повторяют и "С замечанием": движок хранит замечание
владельца у шага (`retry_note`) и добавляет его вместе с ошибкой прошлой попытки (`retryNoteText`) к каждому заданию
агента следующей попытки, а стирает, как только попытка началась. Шагу без агента (`kind: code`) замечание передать
некому, и движок его не принимает; журнал прогона показывает такой повтор правкой владельца.

```ts
async prepare(c) {
  const previous = c.draft as Draft | undefined;
  // Доработка продолжает сессию, в которой агент уже разобрался в задаче.
  const resume = c.feedback && previous ? previous.sessionId : undefined;
  const prompt = resume
    ? renderTemplate(readText(import.meta.url, './rework.md'), { feedback: c.feedback })
    : `${renderTemplate(readText(import.meta.url, './prompt.md'), vars)}\n\n${agentRules(c)}`;
  const r = await c.agent.run({ label: 'план', prompt, cwd: worktreeOf(c), tools: ['Read', 'Grep', 'Glob'], schema: SCHEMA, resume });
  return { sessionId: r.sessionId, ...parse(r.output) } satisfies Draft;
},
```

Агента можно запускать и в `run`, если подтверждать нечего: так работают `code.implement`, который пишет код
в рабочей папке ветки, и `code.verify`, который чинит сборку и проводит ревью. Внешних действий у них нет,
публикует следующий шаг.

## Ожидание внешнего события

Шаг, которому нужно дождаться того, что идет минуты, часы или дни (сборка, деплой, мерж PR, ветка от владельца), не
опрашивает внешнюю систему в цикле, а бросает `StepWaiting` из step-kit (`packages/step-kit/src/waiting.ts`) с
понятным сообщением и событием `WaitEvent`. Событие называет, чего ждать, в терминах портов: `pr` - мерж PR,
`plan-branch` и `build` - ветку плана и сборку коммита в Bamboo, `manual-deploy`, `deploy` и `rollout` - деплой,
который запускает владелец, деплой и выкатку на стенде, `branch` - ветку задачи в репозитории, `linked` - деплой
связанных прогонов. У всех, кроме `pr`, есть начало ожидания `since` и срок `deadline` с ошибкой, которую получит шаг,
если событие к сроку не случится: их собирает `timed(since, ms, error)`, а сроки шагов лежат в `WAIT_MS`
(`steps/_shared/wait.ts`).

Это не сбой: движок ставит шагу и прогону статус `waiting` с сообщением в заметке шага и кладет в контекст `waiting`
(шаг, событие, с какого времени ждет и откуда брошено ожидание). Фоновый наблюдатель (`apps/server/src/watch.ts`)
спрашивает порт события, случилось ли оно: сборку, деплой, выкатку и связанные прогоны раз в
`TASK_PILOT_WATCH_FAST_MS` (по умолчанию 30 секунд), PR, ручной деплой и ветку раз в `TASK_PILOT_WATCH_MS` (по
умолчанию 5 минут). Событие случилось - прогон продолжается, срок вышел - шаг падает с ошибкой из события
(`Engine.failWaiting`). Ждущий шаг не выполняется, поэтому перезапуск сервера его не прерывает: после старта прогон
продолжит наблюдатель. Кнопка "проверить сейчас" на экране прогона продолжает его сразу.

Как шаг продолжается, зависит от того, откуда он бросил ожидание. Из `done`, `prepare` или `preview` шаг выполняется с
начала и сам решает, чего ждать дальше: так `task.finish` ждет мержа до подтверждения. Из `run` подтвержденное
действие уже идет (сборка собирается, деплой в очереди): шаг с хуком `resume(c, event)` продолжает его без `done`,
пробного прогона и нового подтверждения и возвращает выходы, как `run`, или ждет дальше; так работают `ci.wait` и
`deploy.stand`. Шаг без `resume` после ожидания из `run` выполняется с начала: так `task.finish`, опубликовав ответы,
снова ждет мержа, а потом просит подтвердить перевод по доске.
Событие, которого шаг ждал перед этим входом, лежит в `c.waited`: по его `since` шаг, ожидая дальше, держит прежний
срок (`sinceOf` в `steps/_shared/wait.ts`). То, что шаг успел сделать до ожидания, он передает третьим аргументом
`StepWaiting`: движок кладет эти выходы в контекст по их контрактам (так `task.finish` отмечает ответы
опубликованными, а `deploy.stand` - созданный релиз). Новый вид события добавляется в `WaitEvent` и в реестр
проверок `Watcher`.

```ts
if (!branch) {
  throw new StepWaiting(`Жду, пока Bamboo заведет ветку плана ${t.plan} для ${t.branch}`, {
    kind: 'plan-branch',
    contour: t.contour,
    plan: t.plan,
    branch: t.branch,
    ...timed(sinceOf(c, 'plan-branch', 'build'), WAIT_MS.planBranch, `Bamboo за 10 минут не завел ветку плана для ${t.branch}`),
  });
}
```

## Фоновый шаг

Обычно шаги прогона идут цепочкой: следующий отмеченный шаг начинается, когда закончился предыдущий. Шагу, который не
нужен следующим шагам и не меняет ветку, ждать своей очереди незачем, особенно когда цепочка сама днями ждет мерж.
Такой шаг помечается `background: true` в манифесте. Движок запускает его, когда он отмечен и в ожидании, все
отмеченные шаги цепочки выше него в пресете закончены (выполнены, уже сделаны, имитированы или пропущены) и его
`requires` есть в контексте, поэтому место в пресете задает самое раннее начало. Дальше шаг идет рядом с цепочкой тем
же порядком: `done`, пробный прогон, `prepare`, `preview`, свое подтверждение и `run`, с общим сигналом остановки
прогона.

У фонового шага свои ограничения, и движок держит их сам. Его агент не пишет в рабочую папку ветки: движок ставит
запуску `writeCwd: false`, потому что ветку в это же время меняет цепочка. Копия доков задачи для агента
(`c.paths.agentDocs`) у фонового шага своя, а `back()` из `stageDocs` возвращает в доки задачи только файлы, которые
агент изменил или создал, поэтому доки, записанные цепочкой за это время, не затираются. Ждать внешнего события
фоновый шаг не может: `StepWaiting` из него - сбой с просьбой сделать шаг шагом цепочки. Петлей фоновый шаг тоже быть
не может, каталог покажет ошибку манифеста: петля перезапускала бы шаги цепочки у нее на ходу. Ждущую цепочку
наблюдатель продолжает и тогда, когда рядом идет фоновый шаг: мерж замечается, пока агент еще готовит страницу.

Упавший фоновый шаг цепочку не останавливает: владелец повторяет или пропускает его из строки шага, а прогон
заканчивается статусом "выполнен", только когда закончены все отмеченные шаги. Отклоненный фоновый шаг становится
заблокированным и сам не стартует снова. Подтверждение фонового шага приходит рядом с подтверждением цепочки:
главная кнопка экрана открывает первое из них и показывает число остальных, строка каждого ждущего шага открывает
свое, а одобрение фонового шага запускает только его. В учете времени фоновый шаг виден в своей строке целиком, а в
суммы прогона входит только время, когда больше ничего не шло; прогноз учитывает его, только если он кончается позже
цепочки (см. `docs/timing.md`). Пример - `steps/wiki.update/`: страница вики готовится и подтверждается, пока
`task.finish` ждет мерж.

## Публикуемые тексты и линтер

Все, что шаг публикует от имени владельца (сообщение коммита, заголовок и описание PR, комментарий в Jira),
показывается на подтверждении в `preview.texts` с `publish: true`. Внутренний документ на утверждение,
например план, идет туда же с `publish: false`: владелец его видит, но линтер его не проверяет. Тексты входят
в хэш подтверждения вместе с `payload`, поэтому изменение любого слова после клика сжигает подтверждение.
`preview.warnings` - то, на что владельцу стоит обратить внимание: удаленные или измененные существующие
тесты, файлы, которые не войдут в коммит. Текст может задать `format`: `markdown` (план, описание PR, страница вики,
отчет QA, ответы ревьюерам) и `jira` (комментарий в Jira) окно подтверждения показывает отрисованными с
переключателем на исходник, текст без формата - как есть. Текст в разметке Jira разбирает `parseJira`
(`apps/web/src/jira.ts`), а миниатюры `!файл|thumbnail!` берутся из файлов артефактов прогона: до публикации их во
вложениях Jira еще нет. Формат в хэш подтверждения не входит. Открытые вопросы агента
шаг отдает в `preview.questions`: у шага с `prepare` окно показывает поле ответа на каждый, и "Переделать" отдает
ответы агенту списком с номерами вопросов вместе с замечанием (`composeAnswers` в `apps/web/src/answers.ts`).

Публикуемый текст шаг обязан сам пропустить через `c.lint(text)`, а показать и опубликовать результат `.text`.
Линтер правит оформление в прозе. Всегда - русское написание Keycloak в любом падеже (Киклок, Кейклоке) на латиницу.
По личному стилю владельца (`style` в `~/.task-pilot/profile.yaml`, `c.texts.style`) - е вместо буквы с двумя
точками, дефис вместо длинных тире (U+2014, U+2013, U+2015) и прямые кавычки вместо типографских (двойных, угловых и
парных одинарных; одиночный апостроф остается); без личного стиля эти правки выключены. Код в обратных кавычках и
блоках кода линтер не трогает. Он блокирует секреты (значения токенов из `~/.claude.json`, JWT, Bearer, приватные
ключи), номера телефонов, адреса почты вне `allowEmails` и имена сотрудников из `lint.yaml` слоев и `lintNames`
личных настроек.

Движок проверяет публикуемые тексты заново. Текст, который линтер еще исправил бы, блокируется как не
прошедший линтер, пустой текст блокируется как пустой, а предупреждения и блокировки добавляются в
`preview.lint`. С блокирующим замечанием
подтвердить нельзя ни в интерфейсе, ни через API: остаются "Переделать" и "Отклонить". То, что линтер
исправил сам, движок не показывает, поэтому шаг кладет эти замечания (`severity: 'fixed'`) в `preview.lint`.

Исключение - публикуемый текст, в котором есть чужие строки: обновляемая страница вики перезаписывается целиком,
а в разделах, которые писали люди, бывают буквальные цитаты с елочками и имена. Такой текст шаг проверяет сам и
помечает `stepLinted: true`: линтер исправляет и проверяет только новые и измененные строки (`keptLines` из
`step-kit`), а все его замечания, в том числе блокирующие, шаг кладет в `preview.lint`. Движок такой
текст заново не проверяет, интерфейс показывает его как публикуемый. Пример - `steps/wiki.update/`.

## Гибридный шаг публикации

Гибридный шаг соединяет агента и код: агент готовит тексты в `prepare`, код шага приводит их к правилам,
показывает на подтверждении и публикует в `run`. Сокращенный пример шага, который создает PR:

```ts
import type { LintIssue, StepModule } from '../../packages/step-kit/src/index.ts';
import { renderTemplate } from '../../packages/step-kit/src/index.ts';
import { agentRules, GIT_READ, readText, worktreeOf } from '../_shared/agent.ts';

/** Тексты PR после линтера и сессия агента для доработки. */
interface Draft {
  sessionId: string;
  title: string;
  description: string;
  fixed: LintIssue[];
}

const SCHEMA = {
  type: 'object',
  properties: { title: { type: 'string' }, description: { type: 'string' } },
  required: ['title', 'description'],
  additionalProperties: false,
};

const step: StepModule = {
  async prepare(c) {
    const previous = c.draft as Draft | undefined;
    const resume = c.feedback && previous ? previous.sessionId : undefined;
    const prompt = resume
      ? renderTemplate(readText(import.meta.url, './rework.md'), { feedback: c.feedback })
      : `${renderTemplate(readText(import.meta.url, './prompt.md'), { key: c.run.issueKey })}\n\n${agentRules(c)}`;
    // Агент только читает: тексты публикует код шага после подтверждения.
    const r = await c.agent.run({ label: 'тексты PR', prompt, cwd: worktreeOf(c), tools: ['Read', 'Grep', 'Glob', 'Bash'], allow: GIT_READ, schema: SCHEMA, resume });
    const o = r.output as { title: string; description: string };
    const fixed: LintIssue[] = [];
    const clean = (text: string) => {
      const l = c.lint(text);
      fixed.push(...l.issues.filter((i) => i.severity === 'fixed'));
      return l.text;
    };
    return { sessionId: r.sessionId, title: clean(o.title), description: clean(o.description), fixed } satisfies Draft;
  },
  async preview(c) {
    const d = c.draft as Draft;
    const branch = c.get<string>('branch')!;
    return {
      title: `${c.run.issueKey}: PR`,
      actions: [`Создать PR ${branch} → ${c.repo.baseBranch}`],
      texts: [
        { id: 'title', label: 'Заголовок PR', text: d.title, publish: true },
        { id: 'description', label: 'Описание PR', text: d.description, publish: true },
      ],
      lint: d.fixed,
      // Все, от чего зависит действие; в настоящем шаге еще коммит и состав файлов.
      payload: { branch, to: c.repo.baseBranch },
    };
  },
  async run(c) {
    const d = c.draft as Draft;
    const bb = c.repo.bitbucket!;
    const pr = await c.ports.scm.createPullRequest(
      { contour: c.repo.contour, project: bb.project, repo: bb.repo },
      { title: d.title, description: d.description, from: c.get<string>('branch')!, to: c.repo.baseBranch, reviewers: bb.reviewers },
    );
    return { pr };
  },
};

export default step;
```

Настоящему шагу нужны еще `done`, который проверяет состояние снаружи (например, открытый PR через
`c.ports.scm.openPullRequests`: список PR из ветки, а `null`, если Bitbucket такой ветки не знает), и
`simulate`. Каждое действие в `run` стоит проверять по текущему состоянию, чтобы повтор после сбоя делал только
недостающее, а разбор состояния держать в `c.scratch`, чтобы `done`, `prepare`, `preview` и `run` одного
выполнения не повторяли его. Полный пример - `steps/code.publish`: коммит только путей из `commitPaths` профиля
(служебные файлы вроде `.claude/` не коммитятся никогда), пуш, PR в базовую ветку и перевод задачи по доске
одним подтверждением. Содержимое подтвержденных файлов там закреплено id блобов: если файл изменился после
клика или хук репозитория переписал коммит, пуш не выполняется. Force push разрешен только после ребейза,
когда у каждого коммита ветки на remote есть эквивалент в локальной ветке. Черновик помнит, какие тексты были
нужны при подготовке: если позже понадобились другие, шаг просит повторить себя.

## Агентный шаг

Агента шаг запускает через `c.agent.run(request)`. Запуск привязан к прогону и шагу: вопросы агента и его
работа видны в ленте этого шага, стоимость и длительность копятся в строке шага. Каждый вызов инструмента агента
открывается в окне всей ленты с входом и ответом из журнала запуска (дифф правки, вывод команды), так что шагу не
нужно самому пересказывать в ленту, какие файлы агент поменял. Поля запроса:

| Поле | Что задает |
|---|---|
| `label` | короткое имя запуска для ленты; по нему `c.agent.lastSession(label)` находит прошлую сессию |
| `prompt` | текст задания |
| `cwd` | рабочая папка агента, обычно рабочая папка ветки (`worktreeOf(c)`) |
| `tools` | встроенные инструменты: `Read`, `Grep`, `Glob`, `Edit`, `Write`, `Bash` |
| `writeDirs` | папки для записи сверх `cwd`, например копия доков задачи из `stageDocs(c)` |
| `writeCwd` | `false` - в `cwd` писать нельзя, только в `writeDirs` |
| `allow` | дополнительные разрешения: правила `Bash(...)` и инструменты MCP |
| `deny` | дополнительные запреты сверх общих |
| `mcp` | MCP-серверы владельца из `~/.claude.json`, которые нужны шагу |
| `schema` | JSON Schema итога: объект по ней приходит в `output` |
| `model`, `maxBudgetUsd` | перекрывают значения из манифеста |
| `resume` | id сессии, которую нужно продолжить |
| `env` | переменные окружения, например `buildEnv(c.repo)` с `JAVA_HOME` из профиля |

Итог запуска: `sessionId`, `output` (объект по схеме), `text` (последний текст агента), `costUsd`,
`durationMs`, `turns` и `denials` - вызовы, в которых агенту отказано. Ошибка агента или завершение без итога
бросают исключение, и шаг падает. `lastSession(label)` возвращает последнюю сессию шага с этой меткой и ее
статус: так `code.implement` продолжает запуск, прерванный остановкой, сбоем или перезапуском сервера.
Возвращаются только сессии, которые CLI действительно начал: запуск, упавший раньше (например, на неверном
пути к CLI), продолжить нельзя, и следующий повтор начинает новую сессию.

Права агента собираются из запроса по схеме из четырех флагов CLI (`apps/server/src/agent/policy.ts`).
`--tools` сужает встроенные инструменты до `tools` и всегда добавляет `ToolSearch`, без которого не загрузить
инструменты MCP. `--allowedTools` заранее разрешает `ToolSearch`, инструменты конвейера, читающие `Read`,
`Grep` и `Glob` из `tools`, запись в `cwd` (если `writeCwd` не `false`) и `writeDirs` правилами
`Edit(/<папка>/**)`, если в `tools` есть `Edit` или `Write` (правило `Edit` действует и на `Write`), и все из
`allow`. `--disallowedTools` жестко запрещает общий список и `deny` шага. Режим `--permission-mode dontAsk`
отклоняет все, что не разрешено заранее, без вопроса.

Общий список запретов (`baseDeny`) закрывает `git push` и `git commit`, флаги git `--output`, `--no-index` и
`--contents` (с ними "читающие" `git log`, `git diff` и `git blame` пишут или читают любой файл), `curl` и
`wget`, чтение `~/.claude.json` с копиями и бэкапами и служебной папки `.data`, а также все пишущие
инструменты MCP-серверов Jira, Bitbucket и Bamboo, имена которых задают профили доски и контуров. Запрет сильнее
разрешения, поэтому
`allow` шага публикацию не откроет. Bash разрешается не целиком, а правилами: `GIT_READ` из
`steps/_shared/agent.ts` дает git только на чтение, `buildRule(c.repo)` - программу сборки из профиля с любыми
аргументами. Инструменты MCP разрешаются поименно (`mcp__<сервер>__<инструмент>`), а сам сервер попадает
к агенту, только если он указан в `mcp`: остальные серверы из `~/.claude.json` агенту не видны.

Правила CLI не защищают от кода, который запускает сама сборка: тест или плагин сборки, написанный агентом,
выполняется дочерним процессом мимо правил. Поэтому команды Bash агента идут в песочнице CLI (`--settings`,
`sandboxSettings` в `policy.ts`): сети нет, писать можно только в `cwd`, `writeDirs`, `~/.m2` и временные
папки, файлы с токенами и `.data` не читаются, а без доступной песочницы команды не выполняются вовсе.
Сборки самого шага (`c.ports.shell.run`) идут в такой же песочнице macOS, поэтому команды сборки должны
работать без сети, например `mvn -o`.

В папки `.claude/` CLI не дает агенту писать даже при явном правиле `Edit(...)`, а рабочие доки задачи лежат
именно там (`<repo>/.claude/<KEY>/`). Поэтому агент работает с копией: `stageDocs(c)` из `steps/_shared/agent.ts`
заново создает папку `c.paths.agentDocs` (`<worktreesDir>/.task-pilot/<repoId>-<KEY>/docs`), копирует в нее
текущие доки задачи и возвращает `{ dir, back() }`. Папку `dir` шаг передает агенту в `writeDirs` и называет
в промпте, а `back()` после успешной работы агента копирует ее обратно в `c.paths.docs`. Если агент упал, доки
задачи остаются нетронутыми. Пути в черновике и контексте шаг указывает настоящие, из `c.paths.docs`.

Чтобы агент не менял код и писал только в папку доков, передайте `writeCwd: false`, как `task.analyze`: запись
остается только в `writeDirs`, даже если ветка открыта прямо в основной папке репозитория.

```ts
const docs = stageDocs(c);
const r = await c.agent.run({
  label: 'план',
  prompt, // называет агенту файл join(docs.dir, 'plan.md')
  cwd: worktree,
  tools: ['Read', 'Grep', 'Glob', 'Edit', 'Write', 'Bash'],
  writeCwd: false,
  writeDirs: [docs.dir],
  allow: [...GIT_READ, ...jiraTools(c, ['jira_get_issue', 'confluence_search'])],
  mcp: [c.jira.mcp],
  schema: SCHEMA,
});
docs.back(); // план теперь в join(c.paths.docs, 'plan.md')
```

Имя MCP-сервера Jira и Confluence шаг не пишет в коде: его задает профиль доски (`c.jira.mcp`, по умолчанию
`atlassian`), а `jiraTools(c, tools)` из `steps/_shared/agent.ts` дает полные имена инструментов этого сервера.

Шагу с `agent.browser: true` доступны еще два инструмента конвейера, их нужно разрешить в `allow`:
`mcp__pipeline__qa_browser` выполняет действия драйвера `cdp.mjs` (`apps/server/src/qa/driver`) в QA-браузере Task
Pilot (скриншоты действием `shot` ложатся в `<artifactsDir>/qa`), `mcp__pipeline__qa_kibana_logs` выгружает логи
через открытую в нем вкладку Kibana. Сам браузер шаг запускает через `c.ports.browser.ensure()`, а песочница
агента остается без сети: драйвер запускает сервер. Как проверять на стенде, агент читает в скилле теста на стенде
команды: его папку дает `teamSkill(c, 'qa')` из `steps/_shared/team.ts`, а без скилла в `team.yaml` шаг падает с
объяснением, что задать. Пример - `steps/qa.stand/`.

Инструменты конвейера `mcp__pipeline__ask_owner` и `mcp__pipeline__report_progress` доступны агенту всегда.
`ask_owner` задает вопрос владельцу (до восьми вариантов ответа) и ждет ответа в карточке вопроса на странице
прогона; если владелец не ответил за `TASK_PILOT_ASK_TIMEOUT_MS` (по умолчанию 55 минут), агент получает
указание закончить шаг и описать в итоге, какой ответ нужен. `report_progress` пишет короткое сообщение
в ленту. Агент работает под входом владельца в CLI: переменные родительской сессии Claude (`CLAUDE*`,
`ANTHROPIC_*`, `MCP_*`) из окружения убираются, `env` запроса добавляется.

Кнопка "Остановить" срабатывает через `c.signal`. Агента текущего шага движок завершает сам, а сборку
завершает `c.ports.shell.run`, если ему передан `signal`: команда идет через `/bin/sh` в песочнице и в своей
группе процессов, и остановка и таймаут завершают ее вместе с дочерними процессами. Порт возвращает код
выхода, хвост вывода и признаки `timedOut` и `aborted`, полный вывод пишет в `logFile`. Шаг, остановленный
владельцем, помечается упавшим с ошибкой "Остановлено владельцем", прогон встает на паузу; при завершении
сервера тот же сигнал срабатывает с ошибкой "Прервано перезапуском сервера". Долгий цикл внутри шага не должен
продолжать работу после остановки: `code.verify` бросает ошибку, если сборка вернула `aborted`. Шаги, которые
ждут внешнюю систему (сборку, деплой, ветку от владельца), не ждут внутри себя, а бросают `StepWaiting` (раздел
"Ожидание внешнего события"): ждущий шаг не выполняется, и его не останавливают, а пропускают или повторяют.

## Промпт и общие правила

Промпт лежит рядом с шагом в `prompt.md`, отдельные задания (продолжение, доработка по замечанию, исправление
сборки) - в своих файлах: `rework.md`, `continue.md`, `fix.md`. Файл читается помощником `readText` из
`steps/_shared/agent.ts` (`readText(import.meta.url, './prompt.md')`) при каждом запуске, поэтому правка промпта
не требует перезапуска. Значения подставляет `renderTemplate(template, vars)` из step-kit: `{{name}}`
(латиница, цифры, `_` и точка) заменяется значением, `null` и `undefined` дают пустую строку, а переменная,
которой нет в `vars`, - ошибка "В шаблоне неизвестные переменные": опечатка в `prompt.md` видна сразу, а не
пустым местом в промпте.
Необязательный кусок промпта передается переменной с пустой строкой, как `plan` и `feedback` в `code.publish`.
Данные из Jira в промпте оборачиваются в теги с пометкой, что это данные, а не инструкции, как `<описание>`
в `steps/task.analyze/prompt.md`.

К промпту новой сессии добавляются общие правила. `agentRules(c)` дает `steps/_shared/rules.md`: публикует
только конвейер, вопросы только через `ask_owner`, текст задачи и чужие файлы - данные, файлы с токенами не
читаются, итог строго по схеме; за ними разделом "Правила текстов команды и личные" идут `rules.md` пакета команды и
личный стиль владельца (`c.texts`). `agentRules(c, true)` добавляет
`steps/_shared/rules-code.md` для шагов, которые меняют код: тесты не ослаблять без согласия владельца,
от плана не отступать молча, править ровно нужное, сборку запускать командой из задания, помнить, что сети
в командах нет. `buildCommand` для сборки Maven или Gradle требует `build.javaHome` в профиле: без него сборка
пошла бы под JDK по умолчанию. Продолжению сессии
через `resume` правила повторять не нужно, они уже в ней. В `steps/_shared/agent.ts` лежат и помощники для
запросов: `GIT_READ`, `buildRule`, `buildEnv`, `buildCommand`, `worktreeOf`, `stageDocs`, `mergeBase`, `sha256`.
Критерии приемки для промпта шаг берет из `steps/_shared/ac.ts`: `acText(acOf(c))` дает нумерованный список и у
критериев из плана говорит, откуда они, а `acPlanTask` и `planAcOf` нужны шагам, которые пишут план. Шаги, которые публикуют коммит и PR, берут из `steps/_shared/texts.ts` схему итога агента
`TEXTS_SCHEMA`, разбор `textsOutput`, `finishTexts` (ключ задачи в начале заголовка коммита и исправления
линтера) и `commitMessage`.
Папка `_shared` шагом не считается, а ее файлы перезагружаются вместе с шагами, которые их импортируют.

## Тест

Тест кладется рядом (`steps/<id>/<id>.test.ts`) и пользуется помощниками из `steps/_test/context.ts`.
Шаги git проверяются на временных репозиториях (пример - `steps/git.prepare/git.prepare.test.ts`),
шаги Jira - на фейковом порте (пример - `steps/jira.start/jira.start.test.ts`). Прогон: `pnpm test` или
`./node_modules/.bin/vitest run steps/<id>`.

`testContext` собирает `StepContext` из профиля `testRepo(path, worktreesDir)`, портов, значений контекста
(`values`), агента, черновика (`draft`), замечания (`feedback`), параметров, настроек линтера (`lint`) и сигнала,
а журнал складывает в `logs`. Порты, которые шаг не трогает, можно не задавать: обращение к ним падает с именем
порта. Шаг, который опрашивает внешнюю систему, в тесте ждет по `POLL` с маленькими интервалами:
`Object.assign(POLL, { intervalMs: 1 })` в `beforeEach` и возврат сохраненных значений в `afterEach` (пример -
`steps/deploy.stand/deploy.stand.test.ts`).

Агентный шаг проверяется с `fakeAgent(script)`: он сохраняет запросы в `requests`, а `script(req, n)`
возвращает часть итога (обычно `output`) и может сделать то, что сделал бы агент, например записать план
в `req.writeDirs[0]`. Исключение из `script` помечает сессию упавшей, и `lastSession` это видит. В запросе
проверяются права (`allow`, `deny`, `writeDirs`, `mcp`), текст промпта и `resume` при доработке. Движок в тесте
шага не участвует, поэтому его порядок вызовов повторяется вручную: `prepare`, затем `preview` и `run`
с полученным черновиком в `draft` (помощник `gate` в `steps/code.publish/code.publish.test.ts`). Настоящий CLI
claude тесты шагов не запускают.

Порты вики и самого Task Pilot в тестах подменяются так же: `memoryWiki()` из `apps/server/src/demo/wiki.ts` держит
страницы в памяти (пример - `steps/wiki.update/wiki.update.test.ts`), а `PilotPort` с журналом и проверкой по сценарию
задается объектом в тесте (пример - `steps/pilot.retro/pilot.retro.test.ts`).

Для шагов с git `steps/_test/git.ts` дает `branchRepo(key, files)`: временный bare-remote `origin` с веткой
master и рабочую папку с веткой `feature/<KEY>`, а также `gitIdentity` (вызвать в `beforeAll`), `write`,
`commit` и `git`. Временные папки удаляются в `afterEach`. Сборку заменяет фейковый `ShellPort`, который
пишет отчеты surefire по сценарию (пример - `fakeShell` в `steps/code.verify/code.verify.test.ts`).

Шаг целиком, с настоящим агентом, сборкой и подтверждениями, удобно проверить в демо-режиме (`pnpm demo`,
интерфейс на http://127.0.0.1:5187): учебный Java-проект с локальным remote и подмененные Jira, Bitbucket,
Bamboo и логи стендов создаются заново при каждом старте, поэтому во внешних системах ничего не меняется. Задачи
и учебный проект описаны в `apps/server/src/demo/fixture.ts`, подменные Bamboo и Kibana с учебными стендами - в
`apps/server/src/demo/ci.ts`, сквозные тесты пресетов `code-pr`, `test-stand` и `rework` на них - в
`apps/server/test/cycle.test.ts`. Эти тесты и `pnpm demo:script` работают со сценарным агентом `scriptedAgent`
(`apps/server/src/demo/agent.ts`): он узнает шаг по промпту и делает то, что сделал бы настоящий агент. Новому
агентному шагу, который должен пройти в сквозном тесте или сценарном демо, нужна там своя ветка сценария.

## Пресет

Чтобы шаг появился в цикле, добавьте его id в нужные файлы `pipelines/*.yaml` в правильное место: руками или на
экране "Пресеты", который пишет те же файлы и сохраняет в них комментарии. Шаги из поля `off` видны в прогоне, но по
умолчанию не отмечены. Место проверяется по `requires` и `provides`: шаг ставится после шагов, которые дают нужные ему
ключи, иначе редактор пресет не сохранит, а каталог покажет ошибку файла. Ключи, которые есть в прогоне с самого
начала, задает поле `inputs` пресета (по умолчанию `issue` и `ac`; у мастера шагов `stepRequest`). Фоновый шаг
ставится туда, откуда ему можно начинать: он стартует, когда закончены шаги цепочки выше него.

## Мастер "Новый шаг"

Шаг можно не писать руками: кнопка "Новый шаг" на экране каталога заводит прогон `PILOT-<n>` с шагом
`pilot.new-step`. Агент по описанию пишет папку шага по этому гайду, Task Pilot проверяет ее на копии проекта
(`tsc -p steps`, тест шага и тест каталога) и показывает все файлы с итогом проверки на подтверждении. После
подтверждения папка ложится в `steps/` и добавляется в git, каталог подхватывает шаг сразу, коммит - по команде
владельца. Порт или интеграцию, которых нет в `Ports`, мастер не выдумывает: он называет недостающее в итоге.
