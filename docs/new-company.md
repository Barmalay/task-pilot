# Как завести Task Pilot в новой компании

Task Pilot не знает конкретной компании и команды: все, чем они отличаются, описывают профили. Общее для команд
компании - контуры git и Bamboo, защита прода, конфиг деплоя, логи стендов и прода, адрес Jira и id ее полей -
описывает слой компании, свое у команды - ее пакет (`docs/team-pack.md`), личное у каждого человека - файл
`~/.task-pilot/profile.yaml` (`docs/setup.md`). Эта страница о том, что делать, когда Task Pilot приходит в компанию
впервые: проверить, подходит ли стек, собрать данные, решить, где лежат профили компании, описать их и проверить, не
трогая настоящие системы. Образцы - учебный слой `company/example` и учебная команда `examples/demo`.

## Подходит ли стек

Task Pilot ходит во внешние системы через их MCP-серверы и REST и рассчитан на определенный набор систем. Что из набора
нужно, зависит от того, какую часть цикла берет компания:

| Что | Для чего | Без него |
|---|---|---|
| macOS | сборки и команды агентов идут только в песочнице `sandbox-exec` | Task Pilot не работает: для другой системы нужна своя реализация порта `Sandbox` |
| Jira Server или Data Center | доска, задачи, переходы, комментарии и вложения | Task Pilot не работает: без `jira.yaml` сервер не запускается |
| Bitbucket Server или Data Center | PR, ответ на ревью, мерж, git fetch и push по https | PR не создать, ревью и мерж не работают |
| Bamboo | сборка ветки, релизы, деплой на стенды, стенды по правилу | работают только пресеты без сборки и деплоя, например `code-pr` |
| Kibana стендов | подтверждение выкатки по подам и логи теста на стенде | стенды не описать: у каждого стенда обязателен источник логов |
| Elasticsearch прода | экран "Мониторинг", дашборды задач, воронки фич | нет панели мониторинга, шаг `monitor.dashboard` не нужен |
| Confluence | шаг "Вики" (`wiki.update`) | шаг выключается в пресете |
| конфиг деплоя на Ansible (k8s-ansible) | шаг `ansible.config` | шаг не нужен, он и так выключен в пресете `full` |
| CLI Claude Code | агентные шаги | агентные шаги не запускаются |

Прямые запросы к Jira, Confluence и Bamboo идут в REST установок Server и Data Center (`/rest/api/2`,
`/rest/api/latest`) с персональным токеном в заголовке `Authorization: Bearer`, а "кто я" Bitbucket - в
`/rest/api/1.0`. С облачными Jira и Bitbucket Task Pilot не проверялся: авторизация и пути REST у них другие. Другие
системы (GitHub, GitLab, Jenkins, Argo CD) требуют своих адаптеров портов в `apps/server/src/integrations/`. Kibana
стендов должна отвечать на запросы через console proxy без отдельной авторизации: порт логов стендов
(`apps/server/src/integrations/kibana.ts`) ходит без учетных данных.

## Что собрать заранее

Данные компании не угадываются: адреса, id окружений прода и полей Jira берутся из самих систем. Их удобно собрать до
того, как писать профили:

| Что | Где взять | Куда |
|---|---|---|
| Адрес Jira | | `jira.yaml`: `baseUrl` |
| Поля спринта и эпика | `GET <jira>/rest/api/2/field`: поля с `schema.custom` `com.pyxis.greenhopper.jira:gh-sprint` и `com.pyxis.greenhopper.jira:gh-epic-link` | `jira.yaml`: `sprintField`, `epicField` |
| Адреса Bitbucket и Bamboo каждого контура | | `contours/<id>.yaml`: `git`, `bamboo` |
| Имена MCP-серверов | `~/.claude.json` (`docs/setup.md`) | `mcp` контура, `mcp` в `jira.yaml`, `source.mcp` в `monitor.yaml` |
| Окружения прода, резерва и staging | `GET <bamboo>/rest/api/latest/deploy/dashboard/<id проекта деплоя>`: `environment.id` и `name` | `forbiddenBambooEnvIds` контура |
| Имена окружений, похожих на прод | соглашения DevOps компании | `prodLike` контура |
| Теги образов и имена релизов | план и проект деплоя в Bamboo | `builds` контура |
| Kibana стендов | адрес, шаблон индекса, имена полей; id представления данных - в адресе его страницы в Stack Management | `logs.yaml` |
| Кластер логов прода | адрес, ключ только на чтение, Kibana прода | `env` MCP-сервера, `monitor.yaml`: `source` |
| Репозиторий конфига деплоя | проект и репозиторий в Bitbucket | `repos/<id>.yaml`, `deployRepo` у сервисов |
| Имена сотрудников и разрешенные адреса почты | | `lint.yaml` |

## Где лежат профили компании

Слой компании `loadTeam` (`apps/server/src/config.ts`) ищет только в папке `company/<id>` репозитория Task Pilot.
Отсюда два варианта, и выбирает их владелец, потому что первый меняет репозиторий Task Pilot.

Первый вариант - слой компании в своей копии Task Pilot: папка `company/<id>` с профилями компании коммитится в эту
копию, а `team.yaml` каждой команды называет слой полем `company: <id>`. Он подходит, когда команд несколько: общее
описано один раз, и команды его не дублируют.

Второй вариант - без слоя компании: все профили лежат в `profiles/` пакета команды, включая контуры, репозитории
конфига деплоя, `logs.yaml`, адрес Jira и id полей в `jira.yaml` и источник логов прода в `monitor.yaml`. Так устроена
учебная команда `examples/demo`, а репозиторий Task Pilot не меняется. Он подходит для одной команды; когда команд
станет больше, общее переезжает в `company/<id>`, а в `team.yaml` появляется поле `company`.

Правила слияния в обоих вариантах одни (`docs/team-pack.md`): контуры, репозитории, стенды и источники логов слоев
складываются, и одинаковый id в двух слоях - ошибка запуска; ключи `jira.yaml` и `monitor.yaml` команды заменяют ключи
компании; списки `lint.yaml` объединяются.

## Что описать

Файлы слоя компании и их схемы лежат в `packages/step-kit/src/profiles.ts` и `packages/step-kit/src/monitor.ts`.
Обязательные поля указаны в таблице, у остальных есть значение по умолчанию, или они необязательны:

| Файл | Обязательно | Что еще |
|---|---|---|
| `contours/<id>.yaml` (`contourSchema`) | `id`, `title`, `git`, `bamboo`, `mcp`, `connected` | `forbiddenBambooEnvIds`, `prodLike`, `defaultStand`, `builds`, `serviceHeader`, правило стендов `stands`, `deploy`, `note` |
| `repos/<id>.yaml` (`repoProfileSchema`) | `id`, `title`, `contour`, `path`, `worktreesDir` | у репозиториев конфига деплоя - `bitbucket`, `match`, `notes` для агента |
| `stands/*.yaml` (`standProfileSchema`) | `id`, `title`, `contour`, `namespace`, `bambooEnv`, ровно один из `bambooEnvId` и `bambooEnvIds`, `logs`, `deployable` | обычно лежат в пакете команды |
| `logs.yaml` (`logSourcesSchema`) | у каждого источника `kind: kibana`, `url`, `index` | `dataView`, поля текста, логгера, образа и Kubernetes |
| `jira.yaml` (`jiraConfigSchema`) | после слияния слоев `baseUrl`, `myIssuesJql`, `path`, `milestones` | компания дает `baseUrl`, `mcp`, `sprintField`, `epicField`, команда - доску |
| `monitor.yaml` (`monitorProfileSchema`) | после слияния `source` и хотя бы один сервис в `services` | компания дает `source` и `timeZone`, команда - сервисы и `tasksJql` |
| `lint.yaml` (`lintProfileSchema`) | | `names`, `allowEmails` |

Контур - это пара git и Bamboo со своими токенами: токены одного контура в другой не уходят. Поле `bamboo` у контура
обязательно, даже если компания пока берет только пресеты до PR. Контур с `connected: false` описан, но еще не
подключен: шаги с его репозиториями останавливаются и показывают заметку из `note`. Правило `stands` берет стенды
контура из окружений Bamboo, без него стенды контура - только файлы `stands/*.yaml`.

Защита прода держится на трех вещах, и все три стоит заполнить до первого деплоя. Слово prod в namespace или имени
окружения запрещено всегда, имена из `prodLike` запрещены сверх него, а `forbiddenBambooEnvIds` перечисляет окружения
прода по id. Токен Bamboo технически разрешает деплой куда угодно, поэтому в `forbiddenBambooEnvIds` перечисляются все
окружения прода, резерва и staging каждого проекта деплоя контура; стендом по правилу `stands` такие окружения тоже не
становятся.

Ссылки между профилями сверяются при запуске, и ошибка называет профиль. Стенд ссылается на источник логов из
`logs.yaml`, репозиторий и стенд - на существующий контур, `deployRepo` - на репозиторий конфига деплоя того же
контура, `qa.keycloak` - на стенд с адресом и realm. У контура с адресами сервисов на стендах (`stands.serviceUrl`)
должен быть `serviceHeader`, а репозиторий по умолчанию - не больше одного.

## Доступ к системам

Токены в профили и доки не кладутся никогда. Доступ дают MCP-серверы `~/.claude.json` или токены с экрана
"Интеграции", которые хранятся в Keychain (`docs/setup.md`, `docs/integrations.md`). Имена серверов в профилях должны
совпадать с именами в `~/.claude.json`, а сервер, которого там нет, Task Pilot запускает сам с токеном с экрана
"Интеграции". Версии пакетов MCP-серверов стоит закрепить: `pnpm checkup` покажет, на какие.

## Проверка без риска

Профили проверяются по шагам, от того, что ничего не трогает, к настоящим действиям:

1. `pnpm checkup`. Ошибка в профилях называет файл и поле. Строка "Пакет команды" показывает слой компании или "без
   слоя компании", "MCP-серверы" - доступ к каждому серверу из профилей, "Плагин агентов" - скиллы из `team.yaml`,
   "Репозитории" - клоны на местах.
2. Вкладка "Настройки / Интеграции": каждая система отвечает запросом "кто я" под нужным аккаунтом.
3. Экран "Стенды": стенды контуров, их окружения в Bamboo и что на них выкачено.
4. Первый прогон настоящей задачи с отметкой "Пробный прогон, без внешних действий" в карточке прогона: шаги, которые
   меняют что-то снаружи (Jira, git, Bitbucket), только показывают, что сделали бы.
5. Обычный прогон одной задачи с пресетом `code-pr`, который доходит до PR, и только после него пресеты со сборкой и
   деплоем.

`pnpm demo:script` проверяет машину и весь цикл на учебной команде с подменными Jira, Bitbucket и Bamboo, но профили
компании не читает: демо всегда запускается с пакетом `examples/demo`.

## Если это делает Claude

Данные компании - адреса, id окружений прода и полей Jira, имена MCP-серверов - Claude спрашивает у владельца или
читает из самих систем, а не придумывает. Вариант размещения профилей выбирает владелец. Профили пишутся по схемам
выше и сверяются с `company/example` и `examples/demo`. Знание компании не кладется в код, промпты и общие доки Task
Pilot, а токены - ни в какие файлы. Работа закончена, когда `pnpm checkup` проходит без ✗, а пробный прогон настоящей
задачи дошел до конца.
