# Агентные шаги

Шаг запускает агента через `c.agent.run`, а `AgentService` (`agent/service.ts`) превращает запрос в запуск
`claude -p` через `ClaudeRunner` (`agent/claude.ts`): stdin закрыт, вывод stream-json с `--verbose`, вызовы
инструментов и текст агента идут в ленту прогона, итог по `--json-schema` приходит из `structured_output`.
Новая сессия получает свой `--session-id`, продолжение идет через `--resume`. Каждый запуск записывается
в `agent_sessions` (модель, статус, стоимость, длительность, ходы) и получает папку `.data/agent/<id>/`, куда
пишется поток `stream.jsonl` после маскирования секретов.

Права задает `buildClaudeArgs` (`agent/policy.ts`) схемой из четырех флагов: `--tools` сужает встроенные
инструменты до нужных шагу и добавляет `ToolSearch`, без которого не загрузить инструменты MCP;
`--allowedTools` заранее разрешает инструменты конвейера, чтение, запись правилами
`Edit(/<абсолютный путь>/**)` только в рабочую папку (если шаг не передал `writeCwd: false`) и явно указанные
папки и дополнительные правила шага; `--disallowedTools` жестко запрещает `baseDeny` и запреты шага;
`--permission-mode dontAsk` отклоняет все прочее без вопроса. `baseDeny` закрывает `git push` и `git commit`,
флаги git `--output`, `--no-index` и `--contents`, `curl` и `wget`, чтение `~/.claude.json`, его копий и
бэкапов и служебной папки `.data`, а также все пишущие инструменты MCP-серверов Jira, Bitbucket и Bamboo
(`mcpWriteTools`). Имена этих серверов берутся из профилей слоев, а не из списка в коде: сервер Jira - `mcp` доски
(`jira.yaml`), серверы Bitbucket и Bamboo - `mcp` каждого контура. `agentEnv` убирает из окружения переменные родительской сессии (`CLAUDE*`, `ANTHROPIC_*`, `MCP_*`),
и агент работает под собственным входом владельца в CLI или под активным аккаунтом Claude с экрана "Интеграции":
его переменные (`CLAUDE_CONFIG_DIR` папки входа или токен) добавляются последними, и шаг их не подменит. Файлы
входа папок аккаунтов Claude закрыты для агента так же, как `~/.claude.json`: правилами `baseDeny` и песочницей.

Правила CLI не действуют на код, который запускает сборка, поэтому главная защита - песочница. Команды Bash
агента идут в песочнице CLI (`sandboxSettings`, флаг `--settings`): сети нет, писать можно только в рабочую
папку, `writeDirs`, `~/.m2` и временные папки, файлы с токенами и `.data` не читаются, без песочницы команды не
выполняются. Сборки шагов (`integrations/shell.ts`) идут в песочнице порта `Sandbox` (`integrations/sandbox.ts`):
оболочка запускает то, во что `wrap` обернул команду, а без доступной песочницы (`available()`) команду не запускает
вовсе. На macOS это `seatbeltSandbox`: `sandbox-exec` с профилем `sandboxProfile`, сеть закрыта, кроме localhost и
unix-сокетов (они нужны тестам и Mockito), запись и чтение ограничены так же. В профиле не должно быть правила
`(local ip ...)` для исходящих соединений: вместе с DNS через unix-сокет оно пропускает любой трафик. Проверка
окружения спрашивает у того же порта, есть ли песочница.

В папки `.claude/` CLI не дает агенту писать даже при явном `Edit(...)`, а рабочие доки задачи лежат там.
Поэтому агент пишет доки в копию: `stageDocs` (`steps/_shared/agent.ts`) копирует доки задачи в `paths.agentDocs`
(`<worktreesDir>/.task-pilot/<repoId>-<KEY>/docs`), и после успешной работы агента шаг возвращает копию в
`paths.docs`.

Конфигурация MCP пишется на время запуска в `mcp.json` с правами 0600 и удаляется после него, а
`--strict-mcp-config` оставляет агенту только сервер `pipeline` и те серверы владельца из `~/.claude.json`,
которые шаг перечислил в `mcp`, с доступом, который действует на экране "Интеграции" в момент запуска. Сервер `pipeline` (`agent/pipeline-mcp.ts`, stdio) дает инструменты
`ask_owner` и `report_progress` и ходит в API Task Pilot с одноразовым токеном запуска в заголовке
`x-task-pilot-agent`: токен случайный, знает только свой прогон и шаг и перестает действовать, когда запуск
закончился. Вопрос ждет ответа владельца `TASK_PILOT_ASK_TIMEOUT_MS` (по умолчанию 55 минут), таймаут
инструментов MCP у CLI на 5 минут длиннее, чтобы вопрос закрылся сам и агент аккуратно закончил шаг. Вопросы
завершившегося агента закрываются без ответа. Маршруты агентов и решений владельца:

| Маршрут | Кто вызывает | Что делает |
|---|---|---|
| `POST /api/agent/questions` | pipeline по токену | вопрос владельцу |
| `GET /api/agent/questions/:id?wait=<секунды>` | pipeline по токену | ждет ответа, не дольше 60 секунд за запрос |
| `POST /api/agent/questions/:id/expire` | pipeline по токену | агент перестал ждать ответа |
| `POST /api/agent/progress` | pipeline по токену | сообщение о ходе работы в ленту |
| `POST /api/agent/browser` | pipeline по токену шага с `agent.browser` | действия QA-браузера, скриншоты в папку артефактов |
| `POST /api/agent/kibana-logs` | pipeline по токену шага с `agent.browser` | выгрузка логов через вкладку Kibana QA-браузера |
| `POST /api/questions/:id/answer` | интерфейс | ответ владельца на вопрос |
| `POST /api/runs/:id/steps/:stepId/retry` | интерфейс | повтор шага, с `note` - с замечанием агенту шага |
| `GET /api/runs/:id/asks` | интерфейс | вопросы владельца о прогоне с ответами, старые первыми |
| `POST /api/runs/:id/asks` | интерфейс | вопрос о прогоне `question`, ответ агента приходит событием |
| `POST /api/approvals/:id` | интерфейс | решение `approve`, `reject` или `rework` с `comment` |
| `POST /api/runs/:id/stop` | интерфейс | остановка прогона |

Замечание к повтору упавшего или заблокированного шага ("С замечанием" в строке шага) движок хранит у шага и
добавляет вместе с ошибкой прошлой попытки к каждому заданию агента следующей попытки (`retryNoteText`, обертка
агента в `makeContext`); с началом попытки оно стирается. Шагу без агента замечание передать некому: запрос отказывает.

На вопрос владельца о прогоне ("Вопросы о прогоне" на странице прогона, кнопка "Спросить" у шага, который молчит
дольше десяти минут) отвечает агент, который только читает (`AskService`, `ask.ts`). Задание собирает `askPrompt`:
шаги со статусами, заметками и ошибками, ожидание события, последние 150 событий ленты, где лежат код шагов,
документация и рабочая папка задачи, три прошлых ответа прогона и сам вопрос. Агент идет под шагом `pilot.ask` с
моделью sonnet и пределом $0.5 (`ASK_BUDGET_USD`), с инструментами Read, Grep и Glob, без записи, MCP-серверов
владельца и инструментов `ask_owner` и `report_progress`; `quiet` у `AgentService.forStep` не пишет его запуск и
вызовы в ленту. Вопрос и ответ хранятся в таблице `asks` и видны в ленте событиями `ask.asked`, `ask.answered` и
`ask.failed`; пока агент отвечает, второй вопрос по прогону не принимается (409). Ответ, который не успел прийти до
перезапуска сервера, закрывается ошибкой (`markInterrupted`), а стоимость ответа идет в расход агентов, но не в
стоимость прогона. Сценарный агент демо отвечает по шагу, на котором прогон сейчас (`demoAnswer`).

Агент правки мониторинга по запросу (`EditService`, `monitor/edits.ts`) идет вне прогона: `AgentService.forTool` не
пишет его сессию в журнал агентов прогонов (там она ссылалась бы на прогон), не выдает ему токен pipeline и всегда
тихий, а лимиты расхода проверяются и считаются как у шагов: расход записывает сама правка (`onCost`, таблица
`monitor_edits`), и `agentSpendSince` складывает его с расходом сессий. Агент только читает пакет команды и форматы в
`docs/` (Read, Grep, Glob, без записи и MCP) и возвращает новый текст файла по схеме; журнал потока лежит в
`.data/agent/monitor.edit-<id>/`. Подробности - `docs/monitor.md`.
