# Пакет команды и слои профилей

Task Pilot не знает конкретной команды. Все, чем команды отличаются, лежит в пакете команды: ее репозитории и стенды,
доска Jira, сервисы панели мониторинга, дашборды, скиллы агентов и правила текстов. Общее для команд одной компании -
контуры git и Bamboo с их соглашениями, конфиг деплоя, источники логов, адрес Jira и id ее полей - лежит в слое
компании `company/<id>` репозитория Task Pilot. Личное - путь к пакету, логин, JDK, пути на своей машине, стиль
текстов - в `~/.task-pilot/profile.yaml`. Загрузку слоев делает `apps/server/src/config.ts` (`loadTeam`,
`teamLayers`, `loadProfiles`), образец пакета - учебная команда `examples/demo`.

## Как Task Pilot находит пакет

Путь к пакету задает переменная `TASK_PILOT_TEAM`, а без нее - поле `team` личных настроек. Без пакета сервер не
запускается и говорит, что задать. В корне пакета лежит `team.yaml` (схема `teamManifestSchema` в
`packages/step-kit/src/profiles.ts`):

```yaml
id: team
title: TEAM
# Слой компании: папка company/example репозитория Task Pilot; без поля у команды слоя компании нет.
company: example
qa:
  # Скилл теста на стенде в plugin/skills пакета.
  skill: keycloak-stand-qa
  # Логи, которые инструмент qa_kibana_logs дает, когда агент не называет сервис.
  logs: { source: kibana-cloud, container: gate }
wiki:
  skill: wiki-analysis
  # Пространство вики для новых страниц, если в настройке шага "Вики" не выбрано другое.
  space: TEAM
```

Рядом с ним:

| Путь | Что |
|---|---|
| `profiles/repos/*.yaml` | репозитории команды (`repoProfileSchema`) |
| `profiles/stands/*.yaml` | стенды команды, если контур не берет их из Bamboo по правилу |
| `profiles/jira.yaml` | доска команды (ниже) |
| `profiles/monitor.yaml` | сервисы панели мониторинга и задачи на мониторинге (`tasksJql`) |
| `profiles/lint.yaml`, `profiles/logs.yaml` | имена для линтера и источники логов стендов, если они свои у команды |
| `dashboards/<id>/dashboard.yaml` | дашборды задач, формат в `docs/dashboards.md` |
| `features/<id>.yaml` | воронки фич входа на панели мониторинга, формат в `docs/monitor.md` |
| `attempt.yaml` | путь одной попытки входа: сервисы, идентификаторы и что значат строки, формат в `docs/monitor.md` |
| `plugin/` | плагин Claude Code для агентов: `.claude-plugin/plugin.json` и `skills/` |
| `rules.md` | правила текстов команды: агенты получают их вместе с общими правилами конвейера |

## Как складываются слои

Слой компании лежит под профилями команды. Контуры, репозитории, стенды и источники логов слоев складываются, и один и
тот же id в двух слоях - ошибка запуска: профиль одного слоя не подменяет молча профиль другого. В `jira.yaml` и
`monitor.yaml` ключи команды заменяют ключи компании: компания дает адрес Jira, имя MCP-сервера и id полей, команда -
свою доску. Списки `lint.yaml` всех слоев и `lintNames` личных настроек объединяются. Ссылки между профилями
сверяются после слияния: репозиторий команды ссылается на контур и на репозиторий конфига деплоя компании.

Контур слоя компании описывает и соглашения своего Bamboo:

| Поле | Что |
|---|---|
| `prodLike` | имена прода сверх слова prod, которое запрещено всегда, например `reserve\|staging` |
| `defaultStand` | стенд по умолчанию для прогонов, например `^stable` |
| `builds` | теги образов сборок ветки и самого плана (`{build}`, `{branch}`) и имя релиза основной ветки |
| `serviceHeader` | заголовок ответа сервиса со средой: без него адреса сервисов на стендах не проверить |

Стенд с адресом проверяется по пути `health` от своего url (`{realm}` - его realm), у стендов Keycloak это его
well-known.

## Доска

Доска - `profiles/jira.yaml` пакета поверх `jira.yaml` компании. Шаги знают только ключи вех: `jira.start` ведет задачу
к `inProgress`, `code.publish` - к `review`, `qa.publish` - к `testing`, `task.finish` - к `merged`. Какие это статусы,
говорит доска:

```yaml
myIssuesJql: assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC
# Доска для спринтов на экране "Задачи"; без нее экран показывает только "мои задачи".
board: { id: 1061, name: Lifetime Growth Team }
path:
  - { from: Open, to: In Progress }
  - { from: In Progress, to: Code Review }
  - { from: Code Review, id: 31, name: В тестирование, to: QA }
  - { from: QA, to: Done }
offPath: [Blocked]
# Статусы, в которых задача закончена, кроме вехи merged и статусов после нее.
finished: [Closed]
milestones:
  inProgress: In Progress
  review: Code Review
  # null: на этой доске шаг теста задачу не двигает.
  testing: null
  merged: Done
```

Путь - цепочка переходов без разрывов, по ней шаги ведут задачу вперед и никогда назад. id и имя перехода - подсказка:
без них переход находится по статусу, в который ведет (его сообщает REST Jira), а с ними - сначала по id, затем по
имени без учета регистра, кавычек и е с точками. Вехи, которой нет в доске, шаг не найдет и остановится с объяснением;
веха `null` значит, что на этой доске шаг задачу не двигает. Поля спринта и эпика (`sprintField`, `epicField`) задает
слой компании или сама доска, без них спринт и эпик задач не читаются. Колонки экрана "Задачи" - статусы пути, статусы
после него (`after`) и вне пути (`offPath`).

## Как завести пакет команды

1. Скопируйте `examples/demo` в свою папку или репозиторий и поменяйте `id` и `title` в `team.yaml`.
2. Если у компании есть слой в `company/`, назовите его в `company`, а общие профили оттуда из копии уберите.
3. Опишите репозитории команды, стенды (или правило стендов в контуре), доску и сервисы мониторинга.
4. Положите в `plugin/skills` скиллы теста на стенде и страницы вики и назовите их в `team.yaml`; правила текстов
   команды для агентов - в `rules.md`.
5. Укажите путь к пакету в `team` личных настроек и выполните `pnpm checkup`: он проверит пакет, слой компании и
   скиллы, а ошибка в профилях назовет файл.

Знание команды - ее сервисы, стенды, соглашения и слова - место в ее пакете, а не в коде и промптах Task Pilot. Разбор
прогона тоже кладет то, что относится только к команде, в `rules.md` и скиллы пакета.
