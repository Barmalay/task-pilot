# Тест на стенде, доработка и итоги в Jira

QA-браузер - отдельный Chrome, который запускает сам Task Pilot (`createQaBrowser`, `qa/browser.ts`): порт CDP 9343
(`TASK_PILOT_QA_PORT`, в демо 9344), профиль `.data/qa-chrome` (его кэш чистит карточка "Место на диске" на экране
"История"), User-Agent с меткой `TaskPilotQA`. Окно видит
владелец: в нем он решает капчу и вводит коды. Сервер отклоняет любой запрос с этой меткой, поэтому из QA-браузера
нельзя открыть интерфейс или API Task Pilot и подтвердить свой же шаг; Chrome на этом порту без метки - ошибка.
Песочница агента остается без сети: браузером агент управляет только инструментами `qa_browser` и
`qa_kibana_logs` сервера `pipeline`, их маршруты проверяют токен запуска и `agent.browser: true` в манифесте
шага, а сервер сам запускает драйвер QA-браузера (`cdp.mjs`, `kibana_logs.mjs` в `apps/server/src/qa/driver`, другую
папку задает `TASK_PILOT_QA_SCRIPTS`). Драйвер - часть Task Pilot и не знает ни одной команды: сервисы, стенды и
Kibana ему передает сервер из профилей. `checkActions` пропускает только ключи словаря `cdp.mjs`, адреса http и https не на этой
машине и имя скриншота без путей; скриншоты ложатся в `<artifactsDir>/qa`.

`qa.stand` проверяет AC на стенде из шапки прогона по скиллу теста на стенде команды (`qa.skill` в `team.yaml` ее
пакета, папку дает `teamSkill`): QA-гайд и отчет агент пишет в копию доков, шаг
возвращает их в `.claude/<KEY>/`, код шаг не меняет (`writeCwd: false`), владельца агент зовет через `ask_owner`.
Итог по схеме: по каждому AC сценарий, действие, ожидаемое, итог (пройден, не пройден, частично, не проверен),
факт и файлы доказательств. В контекст идут `qaReport` и `failedAc` (`failedOf`: не пройденные и частично, "не
проверен" кодом не исправить). Если на прошлом круге на этом стенде были непройденные AC, следующий запуск
проверяет только их, а итоги сливаются с прошлыми (`mergeResults`). Шаг сделан, если отчет снят на том же стенде
с образом сборки из `deployedBuild` и непройденных AC нет.

`qa.fix` - петля доработки по тесту. Когда непройденных AC нет, шаг "уже сделан", иначе агент в рабочей папке ветки
разбирает отчет, кадры и логи (`qa_kibana_logs`), чинит код и тесты и проверяет сборкой; коммитить он не может.
Если причина не в коде (конфиг, стенд, окружение) или агент ничего не изменил, шаг падает с объяснением. После
успеха движок по разделу `loop` манифеста (`restart: [code.verify, code.publish, ci.wait, deploy.stand, qa.stand]`,
`max: 3`) возвращает эти шаги прогона и сам `qa.fix` в ожидание: новый круг снова проходит проверку, коммит
через подтверждение (текстам коммита шаг передает, что это доработка, `qaFix`), сборку, деплой через
подтверждение и тест только непройденных AC. Четвертый круг движок не начинает: шаг падает "Петля исчерпана", и
дальше решает владелец. В пресете `test-stand` доработки нет: без шагов кода исправление не дошло бы до стенда.

`qa.publish` публикует итоги одним подтверждением. Вложения - файлы из итогов и копия отчета после линтера
`<KEY>-qa-report.md`: тот же файл (имя и размер) пропускается, другой с тем же именем заменяется (Jira кладет
одноименный файл рядом, поэтому старый удаляется), новый загружается. Комментарий с итогами шаг
собирает сам (`commentBody`: таблица `||AC||Сценарий||Действие||Ожидаемый результат||Итог||Факт||` с миниатюрами;
у критериев из плана, которых нет в описании задачи, в колонке AC рядом с номером стоит формулировка, `acLabel`),
агент переписывает его только по замечанию владельца (образец итогов команды - `references/jira-format.md` скилла
теста на стенде, если он там есть, иначе агент держится текущего текста и правил промпта); окно подтверждения показывает комментарий так, как его
отрисует Jira, с миниатюрами из папки артефактов; повторная публикация правит прежний комментарий (`qaComment`).
До комментария шаг сверяет, что все упомянутые файлы есть во вложениях, после - отрисовку (`renderedBody`: `<img>`
по числу миниатюр, без неразобранной разметки, расхождение идет предупреждением в ленту), затем переводит задачу
к вехе `testing`. Вложения и комментарии порт Jira делает через REST с токеном MCP-сервера доски (`jiraRestOf`).

Галерея на странице прогона берет `GET /api/runs/:id/artifacts` (файлы `<artifactsDir>/qa` со сверкой по вложениям
Jira: тот же файл, другой файл с тем же именем или нет) и `GET /api/runs/:id/artifacts/:name` (картинка inline,
остальное вложением, имя по `ARTIFACT_NAME`). Пока идет шаг с QA-браузером (`agent.browser` в манифесте: `qa.stand`
или `qa.fix`), список перечитывается каждые 5 секунд, а после шагов с `refresh: [artifacts]` (`qa.stand`, `qa.fix`,
`qa.publish`) - по их событию `step.status`.

Сервисы на стенде, у которого вместо адреса Keycloak адреса сервисов (`serviceUrl`; так в учебном слое устроены стенды контура core),
`qa.stand` проверяет отдельным промптом `prompt-service.md`, а путь проверки агент выбирает по каждому AC. Ответы сервиса он проверяет
запросами к его API из вкладки QA-браузера, открытой на адресе сервиса (`eval` с `fetch` того же источника: песочница
агента без сети, новый сетевой инструмент не нужен), и засчитывает только ответ с заголовком среды контура (`serviceHeader`, например `x-environment`), равным
namespace стенда. Входы проверяет через Keycloak, если Keycloak ходит в эту сборку: профиль сервиса задает
`qa.keycloak` (стенд Keycloak и стенд сервиса, в который Keycloak на нем ходит; в тестовом пакете для adapter и
api это `stable` и `core-stable`), и когда сборка стоит на этом стенде сервиса, промпт дает агенту стенд Keycloak с адресом и
realm; сборку на других стендах и сервисы без `qa.keycloak` вход через Keycloak не видит, их промпт ведет только через
API. Логи сервиса
`qa_kibana_logs` выгружает с `service`: сервер по стенду прогона берет индекс, поля записи (`messageField`,
`loggerField` источника логов) и namespace (`serviceLogTarget`, `qa/logs.ts`), без `service` - по источнику и контейнеру из `qa.logs` в `team.yaml`
во всех namespace источника (`defaultLogTarget`), а без `qa.logs` агенту нужно назвать сервис. Ссылки на кадры Kibana по сервису `kibana_url.py` строит с представлением данных источника
(`dataView`), колонками `level,messagetext` и фильтром по namespace. Адреса, заголовок, связи сервисов и поля логов
описаны для агента в справочнике скилла `references/services.md`: этот путь знает промпт шага, поэтому у скилла
теста на стенде команды со стендами сервисов такой справочник должен быть.
