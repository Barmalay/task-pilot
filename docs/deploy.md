# Сборка, конфиг деплоя и деплой

Порт Bamboo (`createBambooRest`) работает только через REST: в MCP-сервере нет создания релиза. Токен и адрес
берутся из `env` MCP-сервера контура (`contour.mcp.bamboo`), `bambooFor` сверяет
хост с `contour.bamboo` и иначе токен не отправляет. Деплой порт отклоняет до запроса для окружений из
`forbiddenBambooEnvIds` контура и для окружений, которых нет среди стендов контура с `deployBlockReason === null`.
Порт логов стендов (`createKibanaLogs`) ходит в console proxy Kibana из `logs.yaml` слоев только агрегациями:
образы подов приложения по namespace за окно времени и ответ стенда. Образ - поле `imageField` источника (по умолчанию
`container.image.name.keyword`), под, namespace, контейнер и время - поля Kubernetes источника (`podField`,
`namespaceField`, `containerField`, `timeField`, без них как у filebeat: `kubernetes.pod.name.keyword`,
`kubernetes.namespace.keyword`, `kubernetes.container.name`, `@timestamp`). Ответ стенда - статус по адресу
`standHealthUrl`: url стенда и путь `health` его профиля, где `{realm}` - realm стенда. Тег образа сборки задает схема
`builds` контура (`imageTag`: `{build}` - номер сборки, `{branch}` - номер ветки плана, отдельный шаблон у сборки
самого плана); без схемы тега нет, и выкатку шаг подтверждает только ответом стенда. Ветку плана, сборку, деплой, выкатку и ветку в репозитории деплоя шаги не
опрашивают сами: они бросают `StepWaiting` с событием и сроком из `WAIT_MS` (`steps/_shared/wait.ts`), а продолжает
их наблюдатель (`docs/adding-a-step.md`, раздел "Ожидание внешнего события"). Ждущий шаг и прогон стоят в статусе
"ждет события" и переживают перезапуск сервера.

`ci.wait` ждет ветку плана и сборку коммита из `code.publish` (без него - вершины ветки на remote). Если сборка
упала, агент разбирает последние строки лога упавшего задания, чинит код в рабочей папке и проверяет локальной
сборкой; в CI исправление уходит повтором "Коммит, пуш и PR". Если причина не в коде, агент код не трогает.

`ansible.config` публикует конфиг деплоя задачи в репозиторий `deployRepo`. Ветка задачи там названа как ветка
задачи в репозитории сервиса (`branch` из контекста): такую скрипт деплоя обычно берет сам, без Customize
Deploy, а в контуре, чей деплой ветку задачи сам не берет (`deploy.ansibleBranch: customize`, в учебном слое - core), превью
предупреждает, что деплой пойдет через Customize Deploy. Шаг
берет эту ветку, если она уже есть на remote, иначе единственную ветку задачи, которую раньше завели кнопкой Create
branch (`pickBranch`: имя по шаблону профиля или ключ задачи с префиксом feature/, bugfix/, hotfix/ или без него), а
без них заводит ветку сам: от базовой ветки, без отслеживания, в отдельной папке `<worktreesDir>/<deployRepo>-<KEY>`.
На remote новая ветка появляется только пушем после подтверждения. Ветка, которая отличается от нужной только
регистром, - ошибка: fetch идет только по ветке задачи и базовой, потому что в DEVOPS/k8s-ansible есть ветки,
различающиеся только регистром, и полный fetch на macOS падает.

Правку конфига дают патчи `<имя репозитория в Bitbucket>*.patch` из доков задачи, если они есть: патч, который не
ложится ни прямо, ни обратно, при своих коммитах в ветке считается ручной версией конфига (предупреждение), без них
- ошибкой, а изменения папки вне патчей не публикуются. Без патча правку пишет агент (запуск "конфиг деплоя",
задание `config.md`): в рабочей папке ветки, с чтением git и кода сервиса (`git -C <папка задачи> diff`, `log`,
`show`), по задаче, плану, изменениям конфигурации сервиса и заметкам профиля репозитория деплоя (`notes`). Он
заполняет все окружения сервиса, включая production и reserve, недостающие значения и ссылки на секреты спрашивает у
владельца, значений секретов не пишет, а в итоге возвращает, что сделал, какие секреты завести и что проверить: это
видно на подтверждении. "Переделать" продолжает его сессию с замечанием, и тексты пишутся заново по новой правке.
Если агент ничего не поменял, шаг падает с его объяснением, и ненужный шаг владелец пропускает. Тексты коммита и PR
пишет второй агент только по именам файлов и переменных (`diffKeys`), значения ему не передаются. Подтверждение
закрывает заведение ветки, коммит, пуш без force и PR и привязано к диффу рабочей папки. Шаг кладет в контекст
`ansibleBranch`; превью предупреждает, пойдет ли потом деплой обычным путем или через Customize Deploy.

`deploy.stand` деплоит сборку из `build` на стенд из шапки прогона. Превью показывает, какой релиз из какой
сборки встанет, что сейчас на стенде и чья там задача; payload содержит номер текущего деплоя стенда, поэтому
чужой деплой после клика сжигает подтверждение, а во время чужого деплоя шаг не предлагается. Релиз берется
готовый или создается (в том числе если его успели создать, пока шаг ждал). Конфиг k8s-ansible скрипт деплоя в
Bamboo берет сам: из ветки с именем ветки релиза (для `feature-TEAM-2799-4` это `feature/TEAM-2799`), а без такой
ветки из master; переменная ветки через REST не передается. Поэтому деплой ставится через REST, если
`ansibleBranch` нет или она названа как ветка релиза (`build.branch`), а превью заранее говорит, из какой ветки
пойдет конфиг: без `ansibleBranch` шаг спрашивает remote `deployRepo` (`git ls-remote`), без `deployRepo` ветка
неизвестна. Для `ansibleBranch` с другим именем Deploy в форме Customize Deploy жмет владелец, а шаг сам находит
этот деплой. Так же идет любая ветка задачи в контуре с `deploy.ansibleBranch: customize` в профиле: и своя
`ansibleBranch`, и ветка с именем ветки релиза на remote `deployRepo`; без ветки задачи деплой идет из master через
REST, как обычно. Ссылка в ленте и в ожидании ведет на страницу формы `deploy.customizeUrl` профиля контура (`{envId}`
и `{versionId}` в адресе заменяются окружением стенда и релизом) с подсказкой, какое окружение, релиз и ветку выбрать,
а без нее - на окружение стенда. Ветка конфига входит в payload подтверждения, после деплоя она сверяется с логом
(`ansibleBranchOf`): несовпадение - ошибка (для Customize Deploy обычно значит, что ветку в
форме не выбрали), а `done` не засчитывает релиз, вставший с конфигом из другой ветки. Выкатка подтверждается самым
новым подом с тегом сборки в namespace стенда и ответом 200 по адресу проверки стенда. Подтверждение одно на деплой: пока Bamboo
деплоит, а под и стенд поднимаются, шаг ждет событий `deploy` и `rollout` (Customize Deploy - `manual-deploy`), а
продолжает его хук `resume` без `done` и нового подтверждения, с релизом в контексте с начала ожидания.

Экран "Стенды" и релизы в селекторе стенда берут данные из `GET /api/stands?repo=` (`standsOf`): последний
деплой каждого окружения из дашборда Bamboo, образ самого нового пода за 180 минут и ответ стенда; недоступный
источник не роняет ответ, а попадает в `errors` стенда. После шага `deploy.stand` интерфейс перечитывает стенды.

Окружение стенда в Bamboo задается одним `bambooEnvId`, если у контура один проект деплоя (в учебном слое - cloud),
или `bambooEnvIds` по id репозитория, если у сервисов свои проекты деплоя и Stable у каждого со своим id (core,
`company/example/README.md`). `standEnvId` дает окружение стенда в проекте деплоя репозитория,
`deployBlockReason` с id репозитория проверяет именно его, а репозиторий без окружения на стенд не деплоится и
стенда не видит (селектор в шапке прогона и экран "Стенды" показывают стенды контура репозитория, где у него есть
окружение). Прод отсекается и по имени: слово `prod` всегда и имена `prodLike` контура (в учебном слое `reserve|staging`) в
namespace или имени окружения. Файл в `profiles/stands` пакета команды описывает один стенд или список; так описаны
в учебном слое стенды контура cloud с адресом и realm. Стенды контура, который берет их из Bamboo (core), в файлах не описаны: профиль контура задает правило `stands` (какие окружения стенды: `include` по имени, начало id,
источник логов, заметки по имени), а список окружений и их id `BambooStands` (`bamboo-stands.ts`) читает из Bamboo -
дашборды проектов деплоя сервисов контура - при запуске и раз в час. `standsFromBamboo` в step-kit собирает из них
стенды: id - начало плюс имя окружения в нижнем регистре, namespace - имя в нижнем регистре, у каждого сервиса свое
окружение; окружение, похожее на прод, или из `forbiddenBambooEnvIds` стендом не становится, даже если подходит под
правило, первым идет стенд по умолчанию контура (`defaultStand`). Последний снимок хранится в базе (`app_settings`, ключ `stands:<контур>`), поэтому
при запуске стенды есть до ответа Bamboo и тогда, когда он не отвечает; сбой или пустой ответ оставляют прежний
снимок и пишут событие `stands.failed` (одна и та же ошибка - один раз), изменение списка - `stands.updated`, по
нему интерфейс перечитывает стенды. Список меняется на месте в общем объекте профилей, стенд из файла с тем же id
важнее, а порт Bamboo контура пересоздается с новым списком разрешенных окружений. Окружения прода остаются в
`forbiddenBambooEnvIds` контура. Стенд по умолчанию у прогона - стенд контура его репозитория по `defaultStand`, при
смене репозитория на другой контур стенд переходит на стенд по умолчанию этого контура.

У стендов с адресами сервисов (core) адреса Keycloak нет, зато у каждого сервиса свой адрес: правило контура
задает `serviceUrl` (`{service}` - репозиторий, `{host}` - namespace стенда после замены `host`), профиль сервиса -
путь здоровья `health`. `serviceCheckUrl` дает адрес проверки, а `serviceAnswers` считает ответом сервиса только ответ
с заголовком среды `serviceHeader` контура, равным namespace стенда (и со статусом 200 при пути здоровья): адрес
сервиса на тестовом стенде, где его нет, может ответить с соседнего стенда, и один код 200 принял бы чужой ответ за
свой. Поэтому контур с `serviceUrl` без `serviceHeader` - ошибка запуска. Так проверяют выкатку `deploy.stand` (подтверждение показывает
адрес, после деплоя шаг ждет ответа самого сервиса и называет стенд, который ответил вместо него) и экран "Стенды";
`probe` порта логов стендов отдает статус и заголовок среды. Как тест на стенде проверяет сервисы на таких стендах, - в
`docs/qa.md`.

Как это устроено в учебном слое компании - конфиг деплоя через Customize Deploy, сверка ветки k8s-ansible по логу
деплоя, имена релизов и веток, токен git, стенды из Bamboo, адреса сервисов и офлайн-сборки сервисов, - описывает
`company/example/README.md`.
